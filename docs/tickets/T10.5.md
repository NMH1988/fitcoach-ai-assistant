### T10.5 Tools offered by the question's domain, and the program check on the chat's answer (M) · status: todo · issue NMH1988/fitcoach-ai-assistant#137
**Serves:** Sprint 3 (`docs/BRIEF_SPRINT3.md`): Sprint 3 review point 5; core 4 (technical implementation); Medium 8 (a guard against misuse); evaluation: how function calling is implemented; Sprint 2 (`docs/BRIEF.md`): core 2 (tool calling), core 3 (security measures relevant to the domain). It changes the owner's decision of 2026-10-29 to offer every tool on every turn (T9.20), so it needs the owner's decision before it starts.
**Depends on:** T10.3 (the query plan's fields), O18 (if the answer prompt needs a line)
**Acceptance criteria** (proposed by Claude on 2026-11-18; awaiting the owner's approval)
- [ ] **The domain is known before the tools are bound.** The turn works out the question's domain (nutrition, training, both or unknown) before the first answer call, by the way the owner picks in the Question phase (see Notes) - unit tests of the router with fake models.
- [ ] **Tools by domain.** `graph._tools()` binds, for a training question, the search and the coach's client and memory tools but not the energy, macro, food or meal plan tools; for a nutrition question, for both or for unknown, every tool as today (no tool is training-only) - `tests/test_agent_graph.py` (the tools a fake model is bound with, per domain).
- [ ] **A program in the chat's answer is caught in code.** `graph.finish()` checks the answer for the shapes of a program only: sets x reps given per exercise, day-by-day or weekday headings, and "training plan" / "Trainingsplan" (the patterns are picked in the Question phase from `config.REVIEW_PROGRAM_PATTERNS`, through one shared function, not a copy; the client-volume and plain-reps patterns are not used, as they would catch a cited range); a range a source gives, cited in the answer, is allowed (PRD feature 26). A match replaces the answer with the fixed no-program sentence of T9.20, in the turn's language, and writes a log event with no text - tests, `tests/test_observability.py`.
- [ ] **No lost answers.** The nutrition and training baselines stay within `config.EVAL_TOLERANCE`; answer texts we write ourselves in the app's style (cited ranges such as "about 10 or more sets per muscle group per week [S1]" and "6-12 reps [S2]", in English and German) pass the check, and program-shaped ones fail it - the owner's evaluation runs (O13) and a test over the written answers (the `good_answer` fields of the evaluation files are grading notes, not answers, so they cannot test this).
- [ ] **Fewer tokens for a training question.** The evaluation's input tokens for the training questions are recorded before and after in `docs/TESTING.md` - the owner's run.
- [ ] **Docs match the code.** `docs/TESTING.md` (Sprint 3 known problem 3), `docs/ARCHITECTURE.md` (the tool loop), `docs/DIAGRAMS.md` (the tool loop), `docs/PRD.md` (the training guardrail now in code too), `docs/SECURITY.md` - review.
- [ ] **Reviews.** `code-reviewer`, `/security-review` (tools and prompts), `compliance-reviewer` (the domain guardrails), each report posted on the PR.
**Notes:** today the query plan is made inside the search tool (`src/agent/search.py`), only when the agent chooses to search, so its topics are not known when the tools are bound. Options for the Question phase: (A) run query translation before the agent on every turn and reuse its plan in the search tool (one call a turn that may not search; the plan's `topics` already exist), (B) a small router node with its own structured output (one more call, one more prompt for the owner to write), (C) the guard's existing domain words (no call, but a heuristic). Claude's suggestion: (A), since the plan is already one cheap call and most turns search. Option (A) also changes D10 (`docs/ARCHITECTURE.md`: the agent decides whether to search), as the plan would be made on every turn, so D10 is the owner's call too. The coach's client tools hold both domains, so they stay offered. The program check reuses patterns written for review text, so the training baseline and the written answers are the tests for false alarms. **Also for the owner (Question phase):** the answer streams into the page before `finish()` runs (`views/chat.py`), so a program the check catches is on screen while it streams and is replaced at the end; either hold the stream back on training turns, or accept the brief display and say so in `docs/SECURITY.md`.
