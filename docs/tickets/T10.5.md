### T10.5 Tools offered by the question's domain, and the program check on the chat's answer (M) · status: todo · issue NMH1988/fitcoach-ai-assistant#137
**Serves:** Sprint 3 (`docs/BRIEF_SPRINT3.md`): Sprint 3 review point 5; core 4 (technical implementation); Medium 8 (a guard against misuse); evaluation: how function calling is implemented; Sprint 2 (`docs/BRIEF.md`): core 2 (tool calling), core 3 (security measures relevant to the domain). It changes the owner's decision of 2026-10-29 to offer every tool on every turn (T9.20), so it needs the owner's decision before it starts.
**Depends on:** T10.3 (the query plan's fields), O18 (if the answer prompt needs a line)
**Acceptance criteria** (proposed by Claude on 2026-11-18; awaiting the owner's approval)
- [ ] **The domain is known before the tools are bound.** The turn works out the question's domain (nutrition, training, both or unknown) before the first answer call, by the way the owner picks in the Question phase (see Notes) - unit tests of the router with fake models.
- [ ] **Tools by domain.** `graph._tools()` binds, for a training question, the search and the coach's client and memory tools but not the energy, macro, food or meal plan tools; for a nutrition question, every tool but no training-only one; for both or unknown, every tool as today - `tests/test_agent_graph.py` (the tools a fake model is bound with, per domain).
- [ ] **A program in the chat's answer is caught in code.** `graph.finish()` runs the review's program and client-volume checks (`config.REVIEW_PROGRAM_PATTERNS`, `config.REVIEW_CLIENT_VOLUME_PATTERNS`, through one shared function, not a copy) on the answer; a match replaces the answer with the fixed no-program sentence of T9.20, in the turn's language, and writes a log event with no text - tests, `tests/test_observability.py`.
- [ ] **No lost answers.** The nutrition and training baselines stay within `config.EVAL_TOLERANCE`, and no good answer of the training set trips the program check - the owner's evaluation runs (O13) and a test over the good answers in `data/eval_questions_training*.json`.
- [ ] **Fewer tokens for a training question.** The evaluation's input tokens for the training questions are recorded before and after in `docs/TESTING.md` - the owner's run.
- [ ] **Docs match the code.** `docs/TESTING.md` (Sprint 3 known problem 3), `docs/ARCHITECTURE.md` (the tool loop), `docs/DIAGRAMS.md` (the tool loop), `docs/PRD.md` (the training guardrail now in code too), `docs/SECURITY.md` - review.
- [ ] **Reviews.** `code-reviewer`, `/security-review` (tools and prompts), `compliance-reviewer` (the domain guardrails), each report posted on the PR.
**Notes:** today the query plan is made inside the search tool (`src/agent/search.py`), only when the agent chooses to search, so its topics are not known when the tools are bound. Options for the Question phase: (A) run query translation before the agent on every turn and reuse its plan in the search tool (one call a turn that may not search; the plan's `topics` already exist), (B) a small router node with its own structured output (one more call, one more prompt for the owner to write), (C) the guard's existing domain words (no call, but a heuristic). Claude's suggestion: (A), since the plan is already one cheap call and most turns search. The coach's client tools hold both domains, so they stay offered. The program check reuses patterns written for review text, so the training baseline is the test for false alarms.
