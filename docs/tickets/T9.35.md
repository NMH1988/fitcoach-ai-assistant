### T9.35 Unmasked LangSmith traces in demo mode only, for the reviewer's demo (S, extra) · status: in review · issue NMH1988/fitcoach-ai-assistant#121
**Serves:** Sprint 3 (`docs/BRIEF_SPRINT3.md`): Hard 2 (an LLM observability tool: what a trace shows when it is read), Sprint 3 reviewer comment 1 ("LangSmith is little used", 2026-11-12); Sprint 2 (`docs/BRIEF.md`): Medium 10 (logging and monitoring). It changes PRD AC-33 (no trace holds a question, an answer, a profile value or a logged value), so it is also flagged for the owner's decision: approved on 2026-11-13.
**Depends on:** T9.8, T9.5 (demo mode)
**Acceptance criteria** (proposed by Claude and approved by the owner on 2026-11-13)
- [x] **Off by default.** With the new flag unset, every trace stays masked by `tracing.mask()` and T9.8's tests pass unchanged - the existing `tests/test_tracing.py`.
- [x] **Unmasked only when four things hold.** `FITCOACH_TRACING` is on, the LangSmith key is set, `FITCOACH_TRACING_DEMO_UNMASKED` is on and `config.demo_mode()` is true (demo mode, so no `[auth]`). Any one missing means the masked client (or no tracing) - a parametrised test over the four.
- [x] **What the demo trace shows.** In that mode a coach's chat turn sends its question, tool arguments and results and answer as they are, to the EU endpoint, in a project of its own (`config.LANGSMITH_DEMO_PROJECT`), each run with the `turn_id` of its log line - a canary test on the payloads.
- [x] **Fails closed.** If demo mode stops being true after the client is installed, or the check raises, or tracing is turned off, the next payload is masked; no unmasked client is built without a key; the key is never in a payload - tests.
- [x] **A notice while it is on.** The page says in English and German that messages go to LangSmith unmasked and that no real data should be entered; it shows only while the unmasked trace is active - AppTest.
- [x] **Docs match the code.** `docs/PRD.md` (AC-33 worded as "except in demo mode, with the owner's flag"), `.claude/rules/security-privacy.md`, `docs/SECURITY.md`, `docs/ARCHITECTURE.md` (tracing), `README.md`, `docs/DEPLOYMENT.md` (never for a public deployment), `.streamlit/secrets.toml.example`, `docs/TESTING.md`, `CLAUDE.md` - read the diff.
- [ ] **Reviews.** `code-reviewer`, `compliance-reviewer` (what goes to a third party, the notice) and `/security-review` (tracing and secrets), each report posted on the PR.
- [ ] **Owner's live check** (O13 style): a coach's question read in the demo project of LangSmith, recorded in words in `docs/TESTING.md` (no screenshot of LangSmith's interface committed, as for T9.8).
**Notes:** owner's request, 2026-11-13, to show a reviewer what a trace holds; all traces were `[masked]`, which is T9.8's design. Chosen form (owner, 2026-11-13): a gated feature in `main`, off by default. The unmasked client is a second client (`tracing.build_demo_client()`) whose anonymizer lets a payload through only while a gate that `configure_tracing()` opens and `config.demo_mode()` are both true; the masked client and `mask()` are untouched. Anyone can type real data into a demo's chat, which the code cannot know: hence the notice. The synthetic users, their store and the knowledge base's CC BY chunks are what an unmasked trace holds otherwise. Delete the demo project in LangSmith after the demo (owner's task). T9.33 (merged before this ticket) already sends the evaluation's experiments unmasked through its own client and `tracing.RunTrace`; this ticket follows its precedent that an error keeps only its class name (`tracing.mask_error_only()`), and leaves the experiments as they are. Not built: unmasked traces for a signed-in user (never), a public deployment (never).
