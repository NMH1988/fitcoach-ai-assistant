### T10.4 Prompt versions on traces, log lines, stored reviews and evaluation results (M) · status: done · issue NMH1988/fitcoach-ai-assistant#136
**Serves:** Sprint 3 (`docs/BRIEF_SPRINT3.md`): Sprint 3 review point 3 (d); Hard 2 (an LLM observability tool); the course's topic of prompt engineering; Sprint 2 (`docs/BRIEF.md`): Medium 10 (logging and monitoring).
**Depends on:** -
**Acceptance criteria** (proposed by Claude and approved by the owner on 2026-11-18)
- [x] **A version per prompt.** Loading a prompt (`graph.load_prompt()`, the review's prompt loading, the query translation's) also returns its version: the first 12 hex characters of the SHA-256 of the exact text the model receives (the language part joined, for the answer prompt); the same text gives the same version, one changed character another - unit tests.
- [x] **On every trace.** `tracing.run_metadata()` carries the turn's prompt versions (e.g. `prompt_answer`, `prompt_query`, `prompt_review`) next to `turn_id`, and `tracing.mask()` keeps a value under these keys only when it is exactly 12 lowercase hex characters and masks any other value (not the general identifier rule, which would let a short word through) - `tests/test_tracing.py` (a version survives the mask; a non-hex value under each key is masked; no other value survives).
- [x] **On the turn's log line.** The new fields are added to `observability.ALLOWED_FIELDS` (IDs, which the rule allows) and to the list in `docs/SECURITY.md` - `tests/test_observability.py`.
- [x] **On a stored review.** Migration 7 (`schema._V7`; earlier migrations never edited) adds a `prompt_version` column to `ai_reviews` (beside `model_version`), `NOT NULL` for new rows, with a fixed value (e.g. `unknown`) for rows written before; `reviews.save_review()` stores it; the export holds it - `tests/test_store_db.py` (an upgrade from each earlier version keeps every row), `tests/test_store_reviews.py`, `tests/test_store_my_data.py`.
- [x] **In the evaluation's results.** The results `.json` (`src/eval_results.py`) and a LangSmith experiment's metadata (`src/experiments.py`) record the prompt versions, so two runs show whether the prompt changed - tests.
- [x] **Docs match the code.** `docs/ARCHITECTURE.md`, `docs/SECURITY.md`, `docs/TESTING.md` (how to compare prompt versions), `.claude/rules/security-privacy.md` (the kept trace keys) - review.
- [x] **Reviews.** `code-reviewer`, `/security-review` (tracing), each report posted on the PR; `compliance-reviewer` too, as the store, the logs and the traces change (a hash of the owner's prompt is no personal data, which the run should confirm).
**Notes:** files: `src/agent/graph.py`, `src/agent/review.py`, `src/rag/query_translation.py`, `src/chat.py` (`load_system_prompt`), `src/tracing.py`, `src/observability.py`, `src/store/schema.py`, `src/store/reviews.py`, `src/store/my_data.py`, `src/eval_results.py`, `src/experiments.py`. A content hash, not a hand-kept number: it cannot be forgotten and needs no release step. The evaluation already records the git commit and a diff hash (T9.21); the prompt version adds which prompt within that commit. `run_metadata()` is built in `run_config()` before the `prepare` node loads the prompts, so the Structure phase decides where the versions are worked out: from the same text the run sends (e.g. the prompts loaded once in `run_turn()` and passed to the graph), never from a second read of the files, which could differ if a file changed between the reads. The review's page may show the version to the coach only if the owner wants it (Question phase; Claude's suggestion: not on the page, as it means nothing to a coach).
