### T10.2 Weekly review: kcal figures as numeric fields, checked against the calorie floor by arithmetic (M) · status: todo · issue NMH1988/fitcoach-ai-assistant#134
**Serves:** Sprint 3 (`docs/BRIEF_SPRINT3.md`): Sprint 3 review point 2; Medium 8 (a guard against misuse); evaluation: error scenarios and edge cases, appropriate security; Sprint 2 (`docs/BRIEF.md`): core 3 (security measures relevant to the domain: the calorie floor).
**Depends on:** O18 (the wording of the two fields' descriptions, and a line on them in the review prompt if the owner wants one)
**Acceptance criteria** (proposed by Claude and approved by the owner on 2026-11-18)
- [ ] **Two numeric fields.** `Recommendation` in `src/weekly_review.py` gains `target_kcal: int | None` (a daily intake the recommendation proposes) and `kcal_change: int | None` (a change to the client's current target, negative for a deficit), each with a `Field(description=...)` (its wording drafted or approved by the owner, as it reaches the model, O18) and a range in config, required and nullable as OpenAI's strict mode asks (no default) - unit tests of the model and of the JSON schema sent.
- [ ] **Checked by arithmetic.** The arithmetic lives in `_safety_checks()`, which `validate()` runs, and fails `calorie_floor` when a nutrition recommendation's `target_kcal` is below `config.CALORIE_FLOOR_KCAL`, or when the client's current target (`metrics["nutrition"]["target"]["kcal"]`) plus `kcal_change` is below it; a `kcal_change` with no current target fails a new code (e.g. `kcal_change_no_target`), so the coach sees it - `tests/test_weekly_review.py` (the reviewer's case: a 300 kcal deficit from a 1,400 kcal target fails; from 1,800 it passes).
- [ ] **The text patterns stay as the fallback.** A recommendation that names a kcal figure in its text and leaves both fields null is checked by today's patterns, unchanged; every existing test of the patterns passes unchanged - the existing tests.
- [ ] **The coach's edit is checked the same way.** The edit form on the weekly review page shows the two fields, the coach can change or clear them, and `check_edit()` gets the review's `metrics` (from `ReviewState.metrics` and `ai_reviews.metrics`; today it takes only the review and the chunks) so `_safety_checks()` runs the arithmetic on the edit as on the draft - tests (a coach's edit of `kcal_change` to -600 from a 1,500 kcal target fails) and AppTest (English and German).
- [ ] **The coach and the client see the figures.** The review page shows a recommendation's fields beside its text (e.g. "Target: 1,800 kcal (-300)"), English and German, in the client's view of an approved review too - AppTest.
- [ ] **Old drafts still load.** A review stored before this ticket (its `draft` JSON without the fields) loads, shows and can be approved or edited - `tests/test_store_reviews.py`.
- [ ] **No figures in logs.** No log line holds a field's value - `tests/test_observability.py` (canary values).
- [ ] **Docs match the code.** `docs/TESTING.md` (Sprint 3 known problem 8), `docs/SECURITY.md`, `docs/PRD.md` (the floor enforced in code on the review's figures), `docs/ARCHITECTURE.md` (D22) - review.
- [ ] **Reviews.** `code-reviewer`, `compliance-reviewer` (the domain guardrails and the limits they use), and `/security-review` (the field descriptions reach the model in the schema, and O18 may add a line to `weekly_review_system.md`), each report posted on the PR.
- [ ] **Owner's live check** (O13): one review drafted for a demo client whose week calls for a kcal change, with the fields filled and checked, recorded in `docs/TESTING.md`.
**Notes:** the draft is stored as JSON (`ai_reviews.draft`), so no migration is needed. `weekly_review_system.md` already leaves the schema to the structured output; the field descriptions carry what each field means, and the owner decides whether the prompt needs a line (O18). A text that says one figure and fields that say another: the fields are checked and shown, the text is the coach's to read; whether to also fail a mismatch is the owner's choice in the Question phase (Claude's suggestion: no, as parsing the text is what this ticket moves away from). Training recommendations keep their own fields (D22) and checks. **Also for the owner (Question phase):** an edit is checked against the target stored with the draft's metrics; if the coach sets a new target (T9.17) between the draft and the edit, the arithmetic could use either; Claude's suggestion: the client's current target, read when the edit is checked, as that is the figure the change applies to. If the owner takes it, the edit criterion also names that read (through `access.authorised_read()`, with its audit row) and fails closed with `kcal_change_no_target` when the read is refused.
