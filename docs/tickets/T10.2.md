### T10.2 Weekly review: kcal figures as numeric fields, checked against the calorie floor by arithmetic (M) · status: todo · issue NMH1988/fitcoach-ai-assistant#134
**Serves:** Sprint 3 (`docs/BRIEF_SPRINT3.md`): Sprint 3 review point 2; Medium 8 (a guard against misuse); evaluation: error scenarios and edge cases, appropriate security; Sprint 2 (`docs/BRIEF.md`): core 3 (security measures relevant to the domain: the calorie floor).
**Depends on:** O18 (only if the owner wants a line on the new fields in the review prompt)
**Acceptance criteria** (proposed by Claude on 2026-11-18; awaiting the owner's approval)
- [ ] **Two numeric fields.** `Recommendation` in `src/weekly_review.py` gains `target_kcal: int | None` (a daily intake the recommendation proposes) and `kcal_change: int | None` (a change to the client's current target, negative for a deficit), each with a `Field(description=...)` and a range in config, required and nullable as OpenAI's strict mode asks (no default) - unit tests of the model and of the JSON schema sent.
- [ ] **Checked by arithmetic.** `validate()` fails `calorie_floor` when a nutrition recommendation's `target_kcal` is below `config.CALORIE_FLOOR_KCAL`, or when the client's current target (`metrics["nutrition"]["target"]["kcal"]`) plus `kcal_change` is below it; a `kcal_change` with no current target fails a new code (e.g. `kcal_change_no_target`), so the coach sees it - `tests/test_weekly_review.py` (the reviewer's case: a 300 kcal deficit from a 1,400 kcal target fails; from 1,800 it passes).
- [ ] **The text patterns stay as the fallback.** A recommendation that names a kcal figure in its text and leaves both fields null is checked by today's patterns, unchanged; every existing test of the patterns passes unchanged - the existing tests.
- [ ] **The coach's edit is checked the same way.** The edit form on the weekly review page shows the two fields, the coach can change or clear them, and `_safety_checks()` runs on the edit as on the draft - tests and AppTest (English and German).
- [ ] **The coach and the client see the figures.** The review page shows a recommendation's fields beside its text (e.g. "Target: 1,800 kcal (-300)"), English and German, in the client's view of an approved review too - AppTest.
- [ ] **Old drafts still load.** A review stored before this ticket (its `draft` JSON without the fields) loads, shows and can be approved or edited - `tests/test_store_reviews.py`.
- [ ] **No figures in logs.** No log line holds a field's value - `tests/test_observability.py` (canary values).
- [ ] **Docs match the code.** `docs/TESTING.md` (Sprint 3 known problem 8), `docs/SECURITY.md`, `docs/PRD.md` (the floor enforced in code on the review's figures), `docs/ARCHITECTURE.md` (D22) - review.
- [ ] **Reviews.** `code-reviewer`, `compliance-reviewer` (the domain guardrails and the limits they use), each report posted on the PR.
- [ ] **Owner's live check** (O13): one review drafted for a demo client whose week calls for a kcal change, with the fields filled and checked, recorded in `docs/TESTING.md`.
**Notes:** the draft is stored as JSON (`reviews.draft`), so no migration is needed. `weekly_review_system.md` already leaves the schema to the structured output; the field descriptions carry what each field means, and the owner decides whether the prompt needs a line (O18). A text that says one figure and fields that say another: the fields are checked and shown, the text is the coach's to read; whether to also fail a mismatch is the owner's choice in the Question phase (Claude's suggestion: no, as parsing the text is what this ticket moves away from). Training recommendations keep their own fields (D22) and checks.
