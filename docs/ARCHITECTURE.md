## 1. Overview

Since Sprint 3 the app is a coach-first workspace with two AI parts, both built with LangGraph (section 17 explains them side by side):

```mermaid
flowchart LR
    G[Guest] --> UI
    C[Coach] --> UI
    Y[Gymer] --> UI
    UI[Streamlit pages per role<br/>chat, clients, client week, diary,<br/>workouts, my week, sharing, my data]
    UI --> GU[Input guard<br/>validation, injection, guardrails, rate limit]
    GU --> CH[Chat agent<br/>ReAct loop over tools]
    CH <--> T[Tools<br/>search, TDEE, macros, food, meal plan;<br/>coach: clients, client week, remember]
    T --> S[Search: query translation,<br/>hybrid retrieval, distance gate]
    S --- KB[(Chroma index<br/>CC BY chunks)]
    T --- USDA[(USDA table<br/>and optional API)]
    UI --> RV[Weekly review workflow<br/>authorise, compute, retrieve,<br/>draft, validate, coach decides]
    RV --- KB
    UI --- ST[(SQLite store<br/>accounts, logs, sharing, reviews)]
    T --- ST
    RV --- ST
    CH -.-> OR{{OpenRouter}}
    S -.-> OR
    RV -.-> OR
```

- **The chat agent** (guests and coaches; D9-D12, sections 2 and 17): each turn passes the input guard, then the model decides in a loop whether to search the knowledge base, call a tool, both, or answer, and stops when it has an answer with a basis or reaches the round limit. The session's earlier turns are its short-term memory; a coach's approved working preferences are its long-term memory. The UI shows the answer with its sources, the tool results, the searches it ran and the token cost.
- **The weekly review** (coaches; D17, section 16): a fixed workflow, not a free agent. It checks access, computes the week's figures in code, searches the evidence for the topics the figures raise, has the model draft the review once (twice if the checks fail), validates the draft in code and pauses until the coach approves, edits or rejects it; only then does the gymer read it.
- **No AI for gymers** (T9.24): a gymer logs food, weight and workouts, chooses what the coach sees, and reads the reviews the coach approved; their data reaches a model only as the week's figures, within the scopes they share (`docs/PRD.md`, "Sprint 3").

Until Sprint 3 one chat turn ran a fixed pipeline: guard, query translation, hybrid retrieval, then an answer step in which the model could call tools (D1, D2). T9.2 rebuilt it as a LangGraph `StateGraph` with the same steps as nodes, and T9.3 made the search one of the agent's tools (D10).

## 2. One chat turn, step by step

1. **UI** receives the message. A `st.status` box shows each step while it runs (the brief's progress indicator).
2. **Input guard** (`src/guard.py`), before any API call: raw input over `MAX_RAW_INPUT_CHARS` is rejected before anything else; then the text is cleaned (Unicode NFC, control and invisible characters dropped, trimmed; this is the text the model gets) and checked for empty or too long input (`MAX_INPUT_CHARS`, after cleaning) and for prompt-injection patterns, which run on NFKC-folded copies (with invisible characters removed and as spaces, and with accents stripped) (English and German, the German since T7.4, written with "ss" for "ß" and matching "ü", "ue" and "u" through `german()` in `src/german.py`; instruction overrides, requests for the hidden prompt, role changes and jailbreak phrases, fake role markers and look-alikes of our `<user_input>`/`<sources>` delimiters, also with attributes, a hyphen or space, or a closing slash, and role lines after Markdown markers such as `**System:**` or `> System:`), then the domain guardrails (`src/guardrails.py`, T5.3, on the same folded copies, in English and German since T7.4: performance-enhancing drug dosing is refused; under 18, pregnancy and breastfeeding, medical conditions and medication, and signs of disordered eating, including a daily intake below `CALORIE_FLOOR_KCAL`, are redirected to a professional with a fixed message; the turn ends as kind `guardrail`), and last the per-session rate limit (`RateLimiter`, kept in `st.session_state`). The rate limit counts accepted questions, one per turn however many model calls the turn makes; rejected input does not count. Rejected input makes no API call and gets a fixed message that never quotes it. A chat turn starts with the graph's `guard` node, which runs these checks and ends the turn on a rejection before any other node runs (T9.2); `run_guarded(text, limiter, call)`, which calls the rest with the cleaned text only when the guard accepts it, stays for other callers.
3. **The agent decides whether to search** (T9.3, D10; `src/agent/search.py`): the answer model (step 5) first gets the question alone with the four tools and `search_knowledge_base`. A research question searches; a food or calculator question calls its tool and searches nothing, so no research passage reaches the model (the Sprint 2 review, point 3); a question about the user's targets may do both, in one round or two. A search takes one argument, the query the model writes (`SearchArgs`: one text of 1 to `SEARCH_QUERY_MAX_CHARS`, 500, characters after stripping, no other field; anything else gets `INVALID_SEARCH_QUERY_MESSAGE` and searches nothing), and runs steps 3a and 4 on that query; at most `MAX_SEARCHES_PER_TURN` (2) searches run in a turn, a later call gets `TOO_MANY_SEARCHES_MESSAGE`. The chunks come back inside a delimited `<sources>` block as the search's tool message (`chat.sources_block()`), escaped like every block. A turn's searches share one `SearchLog` in the run's context: the round's calls run one at a time, so a search numbers its new chunks after the ones before it, even in the same round, and a chunk found again keeps its first label, so the `[S#]` labels stay unique across the turn and the Sources list shows each cited article once. The model's replies stay hidden until the answer has a basis: a search found a relevant chunk or a tool gave a result (`config.BASIS_TOOL_STATUSES`: ok, found, not found, or "profile needed", whose answer points to the "Add your details" button; a refused or failed call does not count; owner's choice of 2026-10-29, after the security review of PR #46). A reply with no tool call before that is never shown, and a round whose searches found nothing with no tool result (`BASIS_TOOL_STATUSES`) ends the turn: both give `NO_SOURCES_MESSAGE` with no further model call (AC-2; owner's choice of 2026-10-29, which replaced T3.5's skip before the answer call: an off-topic question now costs the model's one call that decides, plus a search if it makes one). The profile is never in the messages (owner's choice of 2026-10-29): the energy and meal plan tools read it from the app, so `<profile>`, T3.5's `needs_profile` and the "Profile block sent" badge are gone.
3a. **Query translation** (`src/rag/query_translation.py`, T3.2; since T9.3 inside each search, on the model's query): one call to a small model (`openai/gpt-5-nano`) with structured output (`with_structured_output(QueryPlan, method="json_schema")`, which langchain-openai sends with `strict: true`): 3 rewrites of the question plus optional filters (`topics`, `min_year`, `evidence_tier`). Skipped filters mean "no filter". The same reply carries two required booleans (T3.5): `needs_tool` and `needs_profile` (`StrictBool`, so "yes" or 1 makes the plan unusable); since T9.3 the agent decides on tools and the profile is never sent, so the turn no longer reads them (they stay in the schema and the owner's prompt, O7, until the owner drops them). The owner's prompt (`src/prompts/query_translation_system.md`, O7) is the system message; the query goes only inside `<user_input>` in the user message, escaped with `escape_prompt_data()` like the answer step's, and the messages are built with `SystemMessage` / `HumanMessage`, never a prompt template (T3.4's follow-up criterion); each turn stands alone (no history; owner's choice). `QueryPlan` checks exactly 3 non-blank rewrites of at most `QUERY_REWRITE_MAX_CHARS` (300; checked in Python, so the strict schema keeps to the keywords OpenAI's strict mode lists: no string lengths and no defaults, every field required), topics from `config.TOPICS`, `min_year` within `QUERY_MIN_YEAR_RANGE` and a tier of 1 or 2. A reply that fails the schema, is refused, empty or cut off (`InvalidReplyError`, `ReplyCutOffError`) falls back to the query alone with no filter; any other error (key, credit, rate limit, outage) ends the turn with its message, since the answer would meet it too. The rewrites go only to the search and the "How this answer was found" view, never to the answer model.
4. **Hybrid retrieval** (`src/rag/retriever.py`, `src/rag/hybrid.py`, T3.3; since T9.3 inside each search, where "the question" below is the model's query): for the question and each rewrite (the question is searched too, owner's choice in T3.2; a rewrite that repeats the question or another rewrite, ignoring case, is dropped), a vector search in Chroma and a BM25 keyword search, both with the same metadata filter (keyword search keeps only the IDs Chroma returns for that filter, `filter_ids()`, so the two cannot filter differently). Each search gives a ranked list (top `RETRIEVAL_TOP_K` each); all of them are merged with Reciprocal Rank Fusion (RRF, `1 / (RRF_K + rank)`, `RRF_K` = 60); the top 6 distinct chunks become the context. Vector search decides whether the sources cover the question: keyword search runs only when the question itself has a vector hit within the distance limit below (T3.8; before it, a hit of any rewrite was enough), since a BM25 match has no distance and a shared word alone would let an off-topic question through (owner's choice in T3.3); a chunk found only by keyword then joins the list with no distance. If nothing passes the filter, both searches run again with a looser one (T9.20): a plan whose only topic is `resistance_training` (`config.TRAINING_TOPIC`) runs again with that topic alone (its year and tier dropped; nothing more when it had neither), so the same distance gate holds on training chunks and no nutrition chunk, nor a training chunk found only by keyword, stands in for a missing training source, while a year or tier filter that is too strict still falls back; a plan whose topics are all nutrition runs again over the nutrition topics, so no training chunk joins it; a plan with no topic, with both domains, or no usable plan runs again with no filter; if still nothing, the answer says the sources do not cover the question. A chunk counts only within a cosine distance of `RETRIEVAL_MAX_DISTANCE` (0.62, from live checks on 28 questions: covered questions, short or long, at 0.28-0.54, unrelated ones from 0.70; near-domain ones in between are left to the prompt, which declines or redirects them) of the query that found it, but the question counts as covered only when a chunk is within the limit of the question itself (T3.8): the limit was measured on questions, not rewrites, and T3.5's live checks found that even a short query lands within the limit of some chunks, first boilerplate ones (removed by T3.7), then, after T3.7, others: the rewrite "VAR and offside rule in football" had 6 of 6 chunks within the limit (one article chunk, #6, and five short "Main text" chunks of the correction notice #18a, which T3.7 left in) while the question had none, and the offside question reached the answer model in 2 of 3 runs. Once the question is covered, every rewrite's chunks within the limit join the fused list, so a rewrite still finds passages the question's wording misses; a vague question whose own nearest chunk is further than the limit gets `NO_SOURCES_MESSAGE` even when its rewrites come close (owner's choice in T3.8, option 1 of: the question decides, a stricter limit for rewrites, a chunk close to at least two queries, a prompt rule against acronyms); when none is left the search's `<sources>` says no excerpt is close enough (`NO_SOURCES_BLOCK`), and step 3's rule decides whether the turn goes on (a tool that ran in the same round is a basis) or ends with `NO_SOURCES_MESSAGE` (before T9.3: T4.4's unseen call with the tools when the plan said `needs_tool`, and T3.5's skip of the answer call otherwise); the status never reaches "Writing the answer" then. All the queries are embedded in one call, and the retry without the filter reuses the same vectors. Until T3.3 the vector lists alone were merged by keeping each chunk once at its smallest distance, nearest first; `search()` still does this for vector-only retrieval (`retrieve()` and `scripts/compare_retrieval.py`). The filter is built by `build_filter()`: any of the topics (`$or` of `topics $contains`), `year $gte`, `evidence_tier $eq`, joined with `$and`. "No hits" means nothing within the distance limit, so a filter that keeps fewer but relevant chunks is not dropped. `retrieve()` (one question, no filter) stays for `scripts/live_check_retrieval.py`.
5. **Answer step** (the `agent`, `tools` and `end_round` nodes of `src/agent/graph.py`, with helpers in `src/chat.py`): the chat model (default `openai/gpt-5-mini`) gets the owner's system prompt (`src/prompts/answer_system.md`, read on each turn, followed by the chosen language's part, `src/prompts/answer_language_en.md` or `answer_language_de.md`, T7.2: the language is the app's language control (`en` or `de`; "English | Deutsch" in the sidebar since T9.23), passed to `run_turn(language=...)` as a fixed value, never read from the user's text, and only the owner's fixed text joins the system prompt), one user message holding only the user's message inside `<user_input>`, and, after each search, its tool message with the chunks inside `<sources>` labelled `[S1]`...(T9.3; before it, one user message with `<sources>`, `<profile>` when the plan said `needs_profile`, and `<user_input>`). The energy and meal plan tools read the session's profile from the app, never from the model, and no profile block is sent. Every text and metadata value put in any of these blocks is escaped first (`&`, `<`, `>` as HTML entities, `escape_prompt_data()` in `src/prompt_data.py`), so nothing inside can close or open a block, and the user message is plain content, never a prompt template (T3.4). The four tools and the search are bound with `bind_tools` (only the tools: never the model or `max_tokens`; the answer loop alone, `chat.answer_with_tools()`, has no index and gets no search), and the graph's `agent` node and `ToolNode` run the loop (D9 since T9.2; D2 before it): a reply with tool calls is a round; its calls run (at most `MAX_TOOL_CALLS_PER_ROUND`, 6, of which at most `MAX_MEAL_PLAN_CALLS_PER_ROUND`, 1, is a meal plan check, T4.5; the rest, and arguments that are not JSON, get a fixed refusal), each result goes back as a tool message (its JSON escaped like the blocks), and the model is called again. After `MAX_TOOL_ROUNDS` (4) rounds one last call with `tool_choice="none"` writes the answer, so a turn makes at most 5 model calls; tool calls in that call end the turn with a fixed error. Text the model writes in a tool round is cleared from the screen, and a reply cut off by the token limit is an error whose tool calls never run. Since T9.4 the model also gets the conversation's latest earlier questions and answers, between the system prompt and the question ("The conversation" below); from T3.1 to T9.4 each turn stood alone (owner's choice in T3.1). The `[S#]` labels number a search's chunks in their RRF order, best first (nearest first until T3.3), after the labels of the turn's earlier searches (T9.3); `cited_labels()` reads the labels in brackets (`[S1]`, `[S1, S3]`, `[S1, S2, and S3]`, `[S1 & S2]`, `[S1 und S2]` in a German answer, ranges `[S1-S3]`), ignores any outside 1 to the turn's chunk count, and the Sources list shows one card per cited article with all its labels. An answer cut off by the token limit or empty is an error, not shown half-written. Each reply is streamed (`stream_reply()`): the UI shows the text so far under the status box as it arrives, revealed word by word by `PacedWriter` at most `ANSWER_WORDS_PER_SECOND` (30; 0 turns pacing off), then replaces it with the full result and its sources (owner's request in T3.1). Markdown images are replaced by their alt text before the answer is shown, on every streamed update too, so an injected image cannot send data to another server without a click. A missing or empty prompt file gives `PROMPT_MISSING_MESSAGE` before any API call (`LANGUAGE_PROMPT_MISSING_MESSAGE` for the chosen language's part).
6. **Result** back to the UI: the answer with `[S1]`-style citations, a "Sources" expander (one card per cited article: title, authors, tier, journal, year, licence, link), a "Tool results (n)" expander (one table per tool result, and a stacked bar of the macro split for macro targets), and the token use and cost of the turn. Each search's `SearchDetails` (the model's query, rewrites, filters, whether it fell back or dropped the filters, and the `[S#]` labels it found) is kept in the turn's `TurnResult.searches` (`()` when the model searched nothing, `None` when the turn ended before the model); the Details tab shows each search of the last turn that reached the model, or that it made none ("How this answer was found", AC-3, T9.3), and a sidebar card sums them up (`docs/UI_DESIGN.md`, owner's choice in T3.2).

**The chat graph (T9.2, D9; agentic retrieval T9.3, D10).** `src/agent/graph.py` builds the turn above as a LangGraph `StateGraph`, compiled once; `chat.run_turn()` invokes it with the text (since T9.3 not the profile, which only the tools have; since T9.4 also the conversation's earlier messages as `history`) and gets back only the `TurnResult` (and, since T9.4, the question the guard accepted, which the conversation keeps). Its signature kept its parameters until T9.4, which added `conversation=` ("The conversation" below); since T9.3 the result has `searches` instead of `search`, and no `profile_sent`, so the Details view and `scripts/run_evaluation.py` changed with it. The diagram is generated from the compiled graph (`python -c "from src.agent.graph import mermaid; print(mermaid())"`), and `tests/test_agent_graph.py` fails when this copy differs:

```mermaid

---

	guard(guard)
	prepare(prepare)

	agent -.-> tools;
```

- **State:** a `TypedDict` whose input is the raw text (and, since T9.4, the conversation's earlier messages as `history`) and whose output is the result (and, since T9.4, the question the guard accepted, which the conversation keeps); everything else is private state the caller never gets back: the messages of the request (`add_messages`), the cleaned question, the prompts, whether replies wait for a basis (`tools_only`), the tool runs (`operator.add`), the rounds done and whether a round's searches ended the turn (`stopped`).
- **Context:** what cannot or should not be state is the run's context (`TurnContext`, LangGraph's `context_schema`): the index and model factories (each called at most once a turn, and only after the guard), the tools bound to the session's profile, the rate limiter, the UI's callbacks, the manifest, the language, the turn's `UsageRecorder` and its `SearchLog` (T9.3). The recorder is there, not in state, because a node that raises loses its state update, and an error result keeps the tokens spent before it (T5.1, T1.8; owner's choice of 2026-10-26); the search log, because a round's searches number their chunks one after another, before the round's state updates are applied. Errors are raised out of the graph as before, and `run_turn()` turns them into fixed messages (section 10).
- **Nodes:** `guard` (the checks of step 2; a rejection ends the turn, so a rejected or rate-limited input opens no index and calls no model); `prepare` (reads the three prompt files, four in a coach's chat (T9.7), then opens the index, the translation model and the answer model, in that order, so the same error is reported first as before, and builds the request: the system prompt, the conversation's latest earlier questions and answers that fit `HISTORY_MAX_TOKENS` (T9.4), and the question; never a passage or a profile block); `agent` (one model request: a reply with tool calls goes to the tools, any other reply is the answer, or "not covered" while the answer has no basis; it reports "Searching the research" for a search call and "Using the tools" for the others, on the caller's thread); `tools`, LangGraph's `ToolNode`; `end_round` (ends the turn when the round's searches found no basis, step 3; before T9.3 the fixed `translate` and `retrieve` nodes ran before the agent); `finish` (the result with its source cards from all the turn's searches, the fixed memory line of a coach's turn that proposed or was refused and has no basis (T9.7), or "not covered").
- **The tool loop:** the `ToolNode` hands each call of a reply to `run_checked_call()` (its `wrap_tool_call`), which applies the round's limits (`MAX_TOOL_CALLS_PER_ROUND`, `MAX_MEAL_PLAN_CALLS_PER_ROUND`; a call's place in the round is found by identity, as two calls may share an id) and runs the call through `registry.run_tool_call()`, or a search through `search.run_search()`, so arguments are validated and failures answered with fixed messages as before; LangChain's own `tool.invoke()` is never used, and `handle_tool_errors=False` raises an error of ours to the turn's catch-all. `ToolNode` reads only parsed calls, so `end_round` answers the calls whose arguments are not JSON, after the round's results as before, then counts the round. The edge after `agent` is our own `after_agent()`, not LangGraph's `tools_condition`, because a reply whose only calls are not JSON is a round too (owner's choice of 2026-10-26). The calls of a round run one at a time (`max_concurrency` 1), in order. The longest turn takes `MAX_STEPS` (`3 x MAX_TOOL_ROUNDS + 4` since T9.3) node steps, and the graph's `recursion_limit` is one more (LangGraph counts the input as a step), so a loop past it is a bug the catch-all reports.
- **Threads:** LangGraph runs a step's node on the caller's thread while each step has one node, as every step of this graph does (a later graph with parallel branches loses this), so the progress steps and the streamed answer reach Streamlit from the script's thread; only the tool calls run in a worker thread, and they draw nothing.
- `chat.answer_with_tools()` runs the same `agent`, `tools` and `end_round` nodes as a graph of their own on given messages (the wire tests of the tool loop use it).

**The conversation (T9.4, D12; AC-31).** The app passes `run_turn(conversation=...)` the session's `Conversation` (`src/agent/memory.py`), kept in `st.session_state["conversation"]`, never in `st.cache_resource`, so sessions share nothing and the memory goes with the session. It holds its own `InMemorySaver`, a conversation graph compiled with it, and the current `thread_id`. The conversation graph has three nodes (`approve` since T9.7, reached only when a coach's turn proposed a preference); the diagram is generated (`python -c "from src.agent.memory import mermaid; print(mermaid())"`) and `tests/test_agent_memory.py` fails when this copy differs:

```mermaid
---
config:
  flowchart:
    curve: linear
---
graph TD;
	__start__([<p>__start__</p>]):::first
	turn(turn)
	approve(approve)
	forget(forget)
	__end__([<p>__end__</p>]):::last
	__start__ --> turn;
	approve --> forget;
	turn -.-> approve;
	turn -.-> forget;
	forget --> __end__;
	classDef default fill:#f2f0ff,line-height:1.2
	classDef first fill-opacity:0
	classDef last fill:#bfb6fc
```

- **`turn`** runs the chat graph above on the text with the thread's messages as `history`; the graph's `prepare` node gives the model the latest of them that fit `HISTORY_MAX_TOKENS` (`chat.trim_history()`: LangChain's `trim_messages`, counted approximately with no network call, starting on a question), between the system prompt and the new question. The chat graph is compiled with `checkpointer=False`, so its state (the raw text, the tool calls and results, some of which hold profile values, and the `<sources>` blocks) never reaches the checkpointer. When the turn is answered, `turn` adds two messages to the thread: the question as the model got it (`<user_input>`, escaped) and the shown answer with its `[S#]` citations removed (`chat.strip_citations()`), as the next turn labels its own chunks from S1 again (owner's choices, 2026-10-30). A rejected, redirected, "not covered" or failed turn adds nothing, so a rejected message never reaches a later model call (AC-39); nor does an answer that was only citations. An error the turn raises is caught in `turn` and raised again by `Conversation.run()` after the run, as LangGraph would otherwise save it, with its text, as the task's pending write (code review, round 1). The result goes back to `run_turn()` through the run's context (`ConversationContext.results`), not through state, as its tool runs hold tool results.
- **`forget`** deletes the oldest messages beyond `HISTORY_MAX_MESSAGES` with `RemoveMessage` (what is stored, against what the model sees above), cutting only before a question (`memory.first_kept()`), so an answer is never kept without its question. The thread's earlier checkpoints keep removed messages until "New chat".
- **Each turn still needs its own basis** (step 3, AC-2): a follow-up such as "and for 200 g?" is answered when the model looks the food up again; a reply that rests on the conversation alone is not shown (owner's choice, 2026-10-30).
- **"New chat"** (`Conversation.new_chat()`, the Ask tab's button) deletes the thread from the checkpointer (`delete_thread()`, so `get_state_history()` of the old thread is empty), starts a new `thread_id` and clears the chat, so the summary PDF and the session cost cover the new chat; the rate limit is kept. A pending proposal (below) goes with the thread, never saved.
- **`approve`** (T9.7) is reached only when a coach's turn proposed a preference (`after_turn()`): it pauses the graph with `interrupt({"text": ...})` before anything is written, so `invoke()` returns with the turn's result and the proposal waits in the thread's checkpoint (`Conversation.pending()`, read by the chat on every run, so it survives a rerun). The coach's answer on the card resumes it with `Command(resume={"choice", "text"})` (`Conversation.decide()`): the node runs again from the start, `interrupt()` returns the answer, Save checks the (edited) text again and writes it through the page's `save` (`preferences.save()`), Discard writes nothing; either way the state's `proposal` becomes `config.ANSWERED_PROPOSAL`, so the latest state holds no proposed text. A store error at Save is kept in the run's context, not the checkpoint, and raised to the page. In the turn's graph the tool is answered by `run_checked_call()` through `preferences.propose()` (no tool run; a fixed message for the model), and a turn whose model, asked again after its proposal, gives no answer with a basis ends with a fixed line (`TurnResult` kind `memory`) instead of "not covered", so a request that also asks something is still answered (owner's choice, 2026-11-03; AC-2 holds). `awaiting` in the state routes `turn` to `approve`.
- `scripts/run_evaluation.py` passes no conversation, so each evaluation question stands alone as before. The default durability is used: the turn's graph would inherit `"sync"` and fail on it with no checkpointer (langgraph 1.2.17), and the run waits for its background saves before `invoke()` returns anyway.

## 4. Knowledge base pipeline

**Manifest** (`data/sources.json`): one entry per approved source with `id`, `title`, `authors`, `year`, `journal`, `doi`, `pmcid`, `url`, `license`, `license_url`, `copyright_notice`, `evidence_tier`, `topics`, and for a correction notice `corrects` (the ID of the article it corrects, e.g. #18a corrects #18) (`src/rag/sources.py` validates them). Title, authors, DOI and copyright notice come from each article's own front matter; `url` is the DOI link. There is no `fetch_url`: the script builds the Europe PMC URL from the checked PMCID, so the manifest cannot point it anywhere else. `ATTRIBUTION.md` is generated from it (`scripts/generate_attribution.py`); a test fails while the committed file is out of date.

**Download** (`scripts/download_sources.py`):
- Articles with a PMCID come from the Europe PMC REST API as JATS XML (`https://www.ebi.ac.uk/europepmc/webservices/rest/<PMCID>/fullTextXML`). Tested on 2026-10-19 for PMC5477153: HTTP 200, XML with a `<license>` element.
- Source #1 (diets for body weight reduction, 2026) had no PMCID at first; by T2.1 (2026-10-19) Europe PMC had it as PMC13665703, so it is downloaded like the others and the hand-saved fallback was dropped. Scripted access to tandfonline.com is never used.
- **Access terms:** the script uses only the Europe PMC REST API (allowed for automated retrieval by Europe PMC's copyright page); it never scrapes the PMC, Europe PMC or publisher websites. It sends a descriptive User-Agent, waits between requests and never follows a redirect (a 3xx is an error), so no request leaves the REST API.
- **Copyright guard in code:** the script reads the `<license>` element of the article's own front matter (a link, an `ali:license_ref` or a URL in the text) and refuses the file if it names any other Creative Commons licence (NC, ND, SA), a machine-readable licence ID (`license/@xlink:href`, `ali:license_ref`) that is not Creative Commons, wording that contradicts CC BY ("NonCommercial", "NoDerivatives", "ShareAlike", "All rights reserved", "BY-NC"/"BY-ND"/"BY-SA", with any hyphen, a space or nothing between the parts; the `license-type` attribute counts too), a ported licence (e.g. `/by/3.0/us/`), no CC BY or CC0 licence, a licence other than the manifest's, a DOI other than the manifest's, or authors other than the manifest's (T9.21: the contributors of the article's front matter in order, editor groups, non-author `contrib-type`s and roles naming an editor left out; names compared without case, dots and repeated spaces). CC BY wins over CC0 when both appear (BioMed Central's CC0 waiver covers the data, not the text). A refused file is never written, an older copy of it is deleted, and the run exits with 1. Raw XML stays in `data/raw/<PMCID>.xml` (gitignored).

**Parsing** (`src/rag/ingest.py`, standard library `xml.etree`): `load_chunks()` reads `data/raw/<PMCID>.xml` for every manifest entry, runs the T2.1 licence and DOI check, and the T9.21 author check (`check_article()`) again, then parses. It keeps the article title, the abstract and the body sections (section titles, paragraphs, list items as "- " lines). It drops figures, tables, display formulas, supplementary material, the reference list, footnotes, labels and anything that carries its own `<permissions>` (third-party content), as the copyright policy requires (text only, rules 5 and 7). Inline formulas keep their plain text so sentences stay whole, with scripts, fences and accents written out (`I^2`, `β_x`, `P(>0)`, `R̂`); other superscripts are written as exponents too (`10^-3`, `kg^-1`), so numbers keep their meaning. The XML's own line breaks and indentation become single spaces. Numeric citation markers (`xref` to the reference list) are removed with the brackets they leave, and only those brackets (text brackets such as `(-)-epicatechin` stay); an author-year citation keeps its words. Passages credited to someone else (`<attrib>`) are dropped like those with their own `<permissions>`. Back matter that many articles put inside `<body>` (acknowledgements, funding, disclosures, author contributions, data availability, ethics, publisher's notes, supplementary, references, appendices) is dropped by `sec-type` or title, and so are an abstract's registration notes ("Clinical trial registration", "Systematic review registration", "Trial registration": a bare registry ID that short queries matched, T3.7; a Methods "Protocol and registration" section stays) (lists in `src/config.py`). `<back>`, `<floats-group>` and sub-articles are never read. A section is the innermost `<sec>` holding text; its title is the path of titles ("Protein timing > Pre-exercise"), abstract sections start with "Abstract", and paragraphs outside any section (the correction #18a) are titled "Main text". A missing, refused or empty article stops the build with an `IngestError` that lists every problem.

**Chunking:** `RecursiveCharacterTextSplitter` (langchain-text-splitters), at most 1,000 characters (`CHUNK_SIZE`, the section title included) with up to 150 overlap (`CHUNK_OVERLAP`), split inside a section so a chunk never mixes two sections. A piece shorter than 300 characters (`CHUNK_MIN_CHARS`, title included) is joined to the piece before it in the same section, or else to the one after it, as one passage of the section's text, as long as the result stays within 1,300 characters (`CHUNK_SIZE + CHUNK_MIN_CHARS`; T3.7): the splitter leaves such pieces where a paragraph or a section ends, they were mostly the overlap repeated, and they sat near short, generic queries. Only a section that is short as a whole (an abstract's objective, a one-line result), or a piece whose join would pass 1,300 characters, stays a short chunk. The pieces are placed in the section's text by the code itself, each after the one before it and the last one at the end of the text (LangChain's `start_index` can point at an earlier copy of a repeated sentence); if they cannot be placed in order with nothing skipped, the section's pieces stay as split. Each chunk text starts with its section title for context. Metadata per chunk: `source_id`, `title`, `authors`, `year`, `section`, `topics`, `evidence_tier`, `license`, `source_url`, `chunk_index` (from 0 across the article); `authors` and `topics` are lists, which chromadb 1.5.9 accepts. A correction's chunks also carry `corrects` and the corrected article's chunks `corrected_by` (a list), so answers can cite both (copyright policy rule 7); the keys are absent otherwise.

**Topics** (set per source in the manifest): `protein`, `carbohydrate`, `fat`, `energy_balance` (weight loss or gain), `nutrient_timing`, `supplements`, and `resistance_training` (only on the training sources #24-#33, D22, T9.19).

**Embeddings and index** (`scripts/build_index.py`, `src/rag/store.py`): `load_chunks()`'s chunks are embedded with `qwen/qwen3-embedding-8b` through OpenRouter in batches of `EMBEDDING_BATCH_SIZE` (64) and written to the persistent Chroma collection `nutrition-sources` (cosine distance) in `chroma/` (gitignored, D7). Each chunk's ID is `<source_id>-<chunk_index>`, so a rebuild keeps the same IDs; a repeated ID stops the build. A build writes into a staging collection first and gives it the index's name only when every chunk is in, so a failed build (e.g. an API error halfway) leaves the previous index as it was. The collection's metadata records the embedding model; the index is refused if the configured model differs, since query vectors from another model would not match. `open_index()` checks the index first (no API key needed, and it never creates an empty `chroma/`), then opens it with our embeddings client: Chroma's own embedding functions are never used (collections are created and opened with `embedding_function=None`). A missing, unreadable, empty or other-model index raises `IndexNotReadyError`, whose message says to run the build script. List metadata (`authors`, `topics`, `corrected_by`) is stored and returned unchanged, and filters such as `{"topics": {"$contains": "protein"}}`, `{"year": {"$gte": 2020}}` and `$and` work on it (tested). A rough estimate for about 20 articles is a few hundred thousand tokens, which is well under one US cent at the listed price ($0.01 per million tokens on 2026-10-19). The index is built once and rebuilt only when the sources or the chunking change.

**BM25 index** (`src/rag/hybrid.py`, T3.3): `build_keyword_index()` reads every chunk's text and metadata from Chroma and builds a `rank_bm25.BM25Okapi` index in memory (about 1,800 chunks), the first time a question needs it; the app keeps it with `st.cache_resource` and clears it together with the Chroma index when the index stops working. Texts are split into lower-case words of letters and digits, single characters and a short list of English filler words (`STOPWORDS`) are dropped, and there is no stemming, so "HMB" and "B12" stay searchable as written. Only ASCII letters count, which suits the English sources: an accented word is split, and the lone letter of "vitamin D" is dropped. T7.2 (German answers) should check this for German questions, which are searched as typed as well as through their English rewrites. Chunks with no shared word (a score of 0 or less) are not returned.

## 5. Query translation and structured retrieval

- **Why:** users ask short or vague questions ("bulk diet?"). Several rewrites ("energy surplus for muscle gain", "protein intake during a bulking phase", ...) find chunks that one phrasing would miss. They widen the search for a question the sources cover, but do not decide whether they cover it: that is the question's own nearest chunk (T3.8), as one rewrite of an off-topic question can drift into the domain.
- **How:** one structured-output call returns `{"queries": [3 strings], "topics": [...], "min_year": int | null, "evidence_tier": 1 | 2 | null}`. The filters are the brief's "structured retrieval": Chroma's `where` filter and the same filter on the BM25 candidate set.
- **Hybrid search (Hard 1):** vectors catch meaning, BM25 catches exact terms (food names, "HMB", "creatine monohydrate"). RRF merges the ranked lists without needing comparable scores: each chunk scores the sum of `1 / (60 + rank)` over the lists it appears in. **Per-source cap (T8.3):** after ranking, a source keeps its best `MAX_CHUNKS_PER_SOURCE` (3) chunks before the cut to `RETRIEVAL_TOP_K` (6), so one article cannot fill every place (the Sprint 2 review's point 4); chunks over the cap fill the list in fused order only when too few other sources are left, after the kept chunks. The candidate lists are not longer than before (`RETRIEVAL_TOP_K` each), so a source that no list ranks in its top six still cannot get in. In the live check of 2026-10-26 q5 and q10 still missed their second source (#12, #8) in the app. The owner's depth measurement the same day (O13: the question searched alone, lists up to 30 long) shows two different causes. For q10, #8 is in neither the 30 nearest vector chunks nor the top 30 by keyword, so no longer list brings it in. For q5, #12 is already in the fused top 6 at the current list length, so its miss in the app comes from what the app adds to the search, the query translation step's rewrites and topic filters, which change from run to run (in the T8.4 baseline run q5 found #12 once in three askings, with the narrower topic filter; no tier filter was set in any of them). Applying the rule the owner approved on 2026-10-26 (lengthen the lists only if both sources reach the top 15-20), the lists stay `RETRIEVAL_TOP_K` long and T8.4's baseline is taken on this retrieval (`docs/TESTING.md`, "Candidate depth (T8.3 follow-up)").

## 6. Tools

| Tool | Input (validated with Pydantic) | Output | Personal data | Where the numbers come from |
|---|---|---|---|---|
| `calculate_tdee` | weight kg, height cm, age, sex, activity level | BMR and TDEE in kcal/day | yes (profile) | Mifflin-St Jeor equation (#22) times an activity factor (#23) |
| `calculate_macro_targets` | weight kg, goal, TDEE | kcal target and the sources' kcal range; protein, carbohydrate and fat in g, % and g/kg; the protein range; notes | yes (profile) | goal adjustments and macro ranges from #1, #9, #11, #12; enforces the calorie floor |
| `lookup_food_nutrition` | food name, amount in g | kcal, protein, carbs, fat, fiber, plus the matched USDA name and close alternatives, and where the values came from (`source`, `origin`, `data_type`, `api_code`, T9.9) | no (the food name goes to USDA's API when the table lacks it, T9.9) | USDA FoodData Central Foundation Foods (CC0), fuzzy name match with rapidfuzz; for a food not in it, the FoodData Central API (Foundation, SR Legacy, Survey (FNDDS); CC0), ranked with the same match (T9.9) |
| `evaluate_meal_plan` (T4.5) | list of 1-20 foods with grams (the targets come from the profile, not the model) | each food's match and values; totals; per nutrient the target and the gap; kcal and protein against the sources' ranges; notes | yes (profile, through the targets) | the food lookup and `calculate_macro_targets` |

- **Energy tools** (`src/tools/energy.py`, T4.2; values and source IDs in `src/config.py`): BMR = 10 x kg + 6.25 x cm - 5 x age, + 5 for men or - 161 for women (#22); TDEE = BMR x 1.2, 1.375, 1.55, 1.725 or 1.9 by activity level (#23). The kcal target is the TDEE for "maintain", 10% above it for "build muscle" (range 10-20%, #11), and the TDEE minus a weekly loss of 0.5% of body weight for "lose fat" (range 0.5-1.0%, #1, #12), counting about 3500 kcal per lb of fat (#12, a rough estimate). The target is never below the calorie floor, 1200 kcal/day (`CALORIE_FLOOR_KCAL`, the top of the low-energy diet range in #1 and #9); when the floor applies, the message says so, and a note says when the target is at or above the estimated needs. Protein is 2.2 g/kg for fat loss and 1.9 g/kg otherwise (range 1.6-2.2, #1, #11), fat 25% of the kcal (#11, #12) and carbohydrate the rest (#11), at 4, 9 and 4 kcal per g; carbohydrate grams round up, so the macros never add up to less than the target. If protein and fat would exceed the target (only a very heavy body with a low target), protein gets what fat leaves, carbohydrate is 0 and a note says so. Results are Pydantic models with `status` "ok" or "invalid"; invalid arguments get a fixed message naming the fields, never an echo of the input.
- **LangChain tools** (`src/tools/registry.py`, T4.4): `build_tools(profile)` makes four `StructuredTool`s, each with an explicit `args_schema` that holds only what the model may send: `FoodLookupArgs` (`food`, `grams`; `extra="forbid"`, so the tests' `table` hook can never be an argument), `MealPlanArgs` (`items`, a list of those, T4.5) and `NoArgs` for the energy tools. The app reads the profile from `st.session_state` and passes it to `run_turn()`, which builds the tools for it, so the model can neither read nor change it through a tool. `calculate_macro_targets` computes the TDEE from the profile and uses the profile's goal. Without a profile the energy tools and the meal plan tool return "profile needed", and the UI shows an "Add your details" button that opens the profile form.
- **Meal plan tool** (`src/tools/meal_plan.py`, T4.5): `evaluate_meal_plan` looks up each food like `lookup_food_nutrition`, adds up the values shown per food (fiber only over the foods with a reported value), and compares the totals with `calculate_macro_targets`' result for the profile: per nutrient the target and the gap (target minus total), and for kcal and protein whether the total is below, within or above `kcal_range` and `protein_g_range`. Carbohydrate and fat get no range, as the sources give none for them; fiber has no target. Foods not found are listed and left out of the totals (`partial`); a total below the calorie floor (with a pointer to a registered dietitian, like the targets' floor notes) and the targets' own notes come back as notes. The registry builds the targets from the profile (`macro_targets()`, shared with `calculate_macro_targets`), so the model sends only the foods.
- `run_tool_call()` validates every call against the tool's schema before it runs: LangChain skips validation for a schema without fields (`_to_args_and_kwargs` in langchain-core 1.6), so an energy tool called with `weight_kg` would otherwise run. A refused call, an unknown tool, a missing foods table (`FoodTableError`) or any other exception becomes a fixed message the model reads as the tool result (`config.*_MESSAGE`), never the exception's text or what the model sent; the turn goes on, and the UI shows the same message. Results go to the model as JSON in tool messages only, so USDA names never enter the system prompt or the user message.
- **USDA data:** the Foundation Foods CSV zip (about 3.8 MB, release 2026-04-30, checked 2026-10-19) is downloaded by hand into `data/usda/` (gitignored) and turned by `scripts/prepare_usda.py` into `data/usda_foods.csv` (FDC ID, description and per-100 g values), with USDA's suggested credit, the CC0 notice and the changes made as `#` lines on top. The credit text lives in `src/config.py` (`USDA_CITATION`, `USDA_LICENSE`, `USDA_CHANGES`); `scripts/generate_attribution.py` reads the release date from the table and adds the same credit to `ATTRIBUTION.md` under "Food data". CC0 allows committing it, which keeps tests and deployment simple. The table needs no data.gov key; the API below does.
  - Only `foundation_food` rows of `food.csv` are kept (the rest are the lab samples behind them). Nutrient IDs, most preferred first: energy 2048 (Atwater specific factors per food), 2047 (general factors: 4, 9 and 4 kcal per g of protein, fat and carbohydrate), 1008 (older energy ID); protein 1003; carbohydrate by difference 1005; fat 1004; fiber 1079, then 2033. In release 2026-04-30, 312 foods have both 2047 and 2048, 35 only 2047 and 31 only 1008 (which matches 2048 within 1 kcal for 70 of the 98 foods that have both). The owner chose specific factors first (T4.3): they are more exact per food, e.g. raw almonds 584 kcal instead of 626 and creamy peanut butter 589 instead of 632.
  - A food without energy or one of the three macronutrients is left out; a missing fiber value stays empty and is shown as "not reported", never 0. Negative values (carbohydrate by difference for some meat and fish) become 0. Names are Unicode-normalised; a name that appears in several releases is kept once, from the latest publication.
  - Release 2026-04-30 gives 328 foods. Coconut oil and white and whole-wheat bread are in it; olive, canola and the other cooking oils, butter, dry pasta, whey, tofu and most cooked dishes are not. For some of these the tool says "not found"; for others it matches a food that contains the name ("pasta" gives pasta sauce, "olive oil" anchovies in olive oil, "oatmeal" oatmeal cookies), so the model must check `matched_name` before using the values (T4.4).
- **The FoodData Central API** (`src/tools/food_api.py`, T9.9; copyright policy rule 10 as changed on 2026-11-06): the chat's food tool (`build_tools(..., food_api=...)`) looks the food up in the table first; only a `not_found` there, with the owner's key set (`USDA_FDC_API_KEY`, `config.get_food_api_key()`), sends one search to `POST https://api.nal.usda.gov/fdc/v1/foods/search` with a JSON body of the food name and fixed fields (`dataType` Foundation, SR Legacy and Survey (FNDDS), as USDA's pages do not confirm CC0 for Branded and Experimental foods; `pageSize` 25); the key goes in the `X-Api-Key` header and redirects are refused. The name is sent only if it is plain English words with at most 10 words and 4 digits (`api_query()`) and, in a coach's chat, holds no client's full display name as whole words (`client_names`, T9.7's list, `preferences.names_in()`; compliance run 1); otherwise the result is the table's "not found" with `api_code` `name_refused` and a fixed reason that names no one. The key is used only if it is printable ASCII. Each attempt has a 5 s timeout; a timeout, a connection error or a 5xx is tried once more after 0.5 s; a 429 (`rate_limited`), 401 or 403 (`key_rejected`), another 4xx, a refused redirect or an answer that is not a search result (`bad_response`) is not. Each food of the answer is checked (data type, integer ID, a name of at most 200 characters without control, format, surrogate, private-use or unassigned characters, energy in kcal (IDs 2048, 2047, then 1008, as in the table, or their nutrient numbers 958, 957, 208), protein, carbohydrate and fat in g, fiber if reported, within per-100 g bounds; negative values become 0), then ranked with the table's own match (`_rank()`), so a score of 80 is a match. A found food carries `origin` `api`, its `data_type` and `source` "USDA FoodData Central API, <data type> (CC0 1.0), https://fdc.nal.usda.gov/"; the line under it in the app and the PDF names the API (`food_source_line()`), and the PDF's credits add the API's credit (USDA's suggested citation from the API guide), as `ATTRIBUTION.md` does, also when the API's names were only offered as suggestions (`no_match`). A failure keeps the table's "not found" with its code and a fixed sentence. One turn makes at most 6 searches (`TurnBudget`, built with the tools once a turn), and none after its first failed search: the turn's later lookups return the same code with no request. The meal plan check, the diary and the Food lookup tab keep to the table (owner's choice, 2026-11-06), and the evaluation run passes no client, so its baseline stays reproducible. Nothing the API returns is stored. `views/chat.py` builds the client on every turn (`build_food_api()`), so a key added to the secrets works without a restart.
- **Food name matching** (`src/tools/food.py`): names are lower-cased, punctuation dropped and simple plurals reduced, then scored with rapidfuzz as the mean of `WRatio` and `token_set_ratio` (either alone gave wrong matches on the real table). A score of 80 or more is a match (`FOOD_MATCH_MIN_SCORE`); 60 or more is offered as an alternative or a "did you mean" suggestion. Among the matches, the plain food beats a processed form the query does not name (flour, oil, juice, dried, powder, milk, butter), then a name whose head (before the first comma) is made of query words ("Rice, white" over "Flour, rice" for "white rice"), then the higher `token_set_ratio` (how fully the query words appear in the name), the higher score and the shorter name. The tool always returns the matched USDA name and up to 3 alternatives, so the model can look up a better one.

## 9. Token usage and cost (Medium 5)

Built in T5.1. `run_turn()` gives each turn a `usage.UsageRecorder`, passed down to every call, so a turn that fails keeps what it spent before the error (`TurnResult.usage`, one `CallUsage` per call: step, model, input, cached input, output and reasoning tokens):

- **Query translation:** `with_structured_output(..., include_raw=True)`; the tokens come from the raw reply. The parser's errors (a refusal, an empty reply) come back as `parsing_error` and still fall back to the question alone, with their tokens counted. A reply the SDK itself cannot parse (off the schema, or cut off) raises inside the call, so its tokens are not known: such a turn shows fewer tokens than it used (rare; pinned by a test).
- **Query embedding:** `build_embeddings()` returns `llm.CountingEmbeddings`, whose `embed_with_usage()` sends the same request as `embed_documents()` but also returns the reply's `usage.prompt_tokens` (langchain-openai 1.7.2 drops it). The count is returned with the vectors, never kept on the client, which all sessions share. One batch without a count makes the whole count unknown (no row), never too low.
- **Answer rounds:** `build_chat_model()` sets `stream_usage=True`: langchain asks for the token use of a streamed reply (`stream_options.include_usage`) only on OpenAI's own URL. `stream_reply()` records each round's usage before its cut-off check, so a reply cut off by the token limit is counted too, as is the hidden reply of a question with no relevant source. An error in the middle of a stream loses that round's count (the usage comes in the last chunk).

The app adds the turn to `st.session_state["messages"]` first, then prices its calls once (`views/usage_view.price()`) and stores the priced `usage.TurnUsage` with it, so a rerun makes no network call, and a click during the price read (which reruns the script) cannot drop the answer from the history. Prices come from OpenRouter's public lists, read without the key: `/api/v1/models` for the chat models and `/api/v1/embeddings/models` for `qwen/qwen3-embedding-8b`, which is only in the second. `usage.PRICES` keeps them for a day for the whole app process; a failed read (5 s timeout, no redirects, a 20 MB cap, a body that is not JSON, a list with no usable price for the app's models) is not kept, so the next turn tries again, and that turn's cost shows "price unknown". Prices are read as exact `Decimal`s; a price that is not a finite number from 0 to `PRICE_MAX_PER_TOKEN` ($0.01 a token, far above any allowed model; so no cost can overflow) leaves the model out (OpenRouter gives "-1" for a varying price), so its calls are "price unknown" rather than wrong.

Cost of a call: uncached input x `prompt` + cached input x `input_cache_read` (`prompt` when there is none) + output x `completion`. The reasoning count is shown as the provider reports it and never priced or added (it can be higher than the output count, so it is not taken to be part of it); `scripts/live_check_llm.py` prints this cost next to the one OpenRouter records (`GET /api/v1/generation`) for a plain call and for one streamed through `chat.stream_reply()` as the answer rounds are (so the owner also sees whether OpenRouter's stream reports the usage once), for the owner to confirm it (O5; T1.2 saw 94 reasoning tokens reported against 86 output tokens). The O5 cost check (2026-10-21, `docs/TESTING.md`) confirmed the uncached-input and output terms on one streamed `openai/gpt-5-mini` call (not the cached-input price, gpt-5-nano or the embedding price): for that call the app recorded the same tokens as OpenRouter (16 in, 83 out, 104 reasoning) and its cost, $0.00017, equals the cost OpenRouter recorded; reasoning is not billed on top of the output tokens, even when its reported count is the larger.

Shown under each answer ("3,700 tokens · $0.0074", "<$0.0001" below a hundredth of a cent), in the sidebar's "Last answer" card (that answer and the session, with "+ price unknown" when some turn could not be priced; before any turn has searched, the session line alone) and in the Details tab (one row per call, then the answer and session totals). Dollar signs are escaped in Markdown, so two on one line never read as LaTeX.

The mapping lives in `src/llm.py`: callers wrap a model or embedding call in `with mapped_errors():`, which turns any OpenAI SDK error, and a malformed reply the client could not read, into an `LLMError` subclass whose message is fixed text (never the server's response, so never the key) and drops the original from the traceback. The original stays on `__context__` and its request holds the key, so it is never logged or shown; each `LLMError` carries a `diagnostic` instead (the error type and the function that raised it, no message text), which is safe to log. Malformed replies raise plain `ValueError`/`KeyError`/`TypeError`, so those are mapped only when the traceback passes through `openai` or `langchain_openai`; a bug of ours that langchain raises is mapped too, and the diagnostic shows where it came from. Each request has a `LLM_TIMEOUT_SECONDS` (60) timeout. Clients are built only through `src/llm.py`, and `model` and `max_tokens` are never passed at call time or changed on a built client (`.claude/rules/security-privacy.md`), so the allowlist and the cap are not bypassed as long as that rule is followed; `tests/test_client_rules.py` scans `src/`, `views/`, `app.py` and `scripts/` for a call-time setting, a pass-through (`model_kwargs`, `extra_body`), a changed or reconfigured client, or a client built outside `src/llm.py` (T9.2; what an `ast` scan cannot see is listed in its docstring).

**Logging (T8.2, Sprint 2 review point 1).** `src/observability.py` sends the app's log lines to stderr as one JSON object per line (`configure_logging()`, called once at the start of `app.py` and of every script's `main()`, except `scripts/capture_media.py` and `scripts/make_video.py`, which write no log lines and import nothing of `src`, as `configure_logging()` reads the secrets file and would put the key in the environment of the browser, Piper and FFmpeg they start (T9.27, owner's decision, 2026-11-09; T9.28; `docs/TESTING.md`, "README images (T9.27)" and "Presentation video (T9.28)"); it keeps a single handler, so Streamlit's reruns add none, and it has no file handler; the level is `config.LOG_LEVEL`). The formatter writes `ts`, `level`, `logger`, `event` and only the fields on its allowlist (`ALLOWED_FIELDS`): an unknown `extra` key is dropped, the event must be one of `observability.EVENTS` (otherwise `unnamed_event`), every value must be plain (text, a number, a boolean, `null` or a flat list of them; an object such as an exception makes the record a `log_failed` line, never its `str()`), and the message's arguments and any exception are never written, so a stray `logger.error(f"... {text}")`, `logger.error("... %s", text)` or `exc_info=True` cannot put text on a line; a record that cannot be written, or a record that cannot be built, leaves the fixed event `log_failed` and the turn goes on. `run_turn()` gives every turn a `turn_id` (a UUID4, carried in `TurnResult`) and writes exactly one INFO record, `turn`, whatever way it ends: `turn_id`, `kind`, `code`, `language`, `chunks` (the chunks the turn's searches gave the model), `source_ids` (their sources, once each), `tools` and `tool_statuses` (a tool the model made up is `null`), `tokens`, `cost_usd` (text, or `null` when a price is not known yet: the turn uses only the prices already read, `usage.PriceCache.peek()`, because reading them is a network call that `views/chat.py` makes after the answer is shown, so the first turn of a process has `null`), `duration_ms` (the whole turn, the paced display of the answer included) and `searches` (how many knowledge base searches the agent ran, T9.3; `profile_sent` until T9.3). The chunks, tool runs and search count are collected as the turn runs (`_TurnTrace`), not read from the result, so a turn that ends in an error after a tool ran still logs it. WARNING records, each with the `turn_id`: `llm_error` (`code`, `status_code`, `diagnostic`), `guard_rejected` (`reason`, `code`: the rejections, the rate limits and the domain guardrails) and `tool_failed` (`tool`, `status` `error` or `invalid`). The chat's food tool (T9.9) writes `food_api` for each lookup that reaches the API step (the table had no match and a key is set), whether or not a request is sent: `found` or `no_match` after a search, `name_refused` or `turn_limit` with no request, and, after the turn's first failed search, the same failure code for each later lookup with no request (so three missing foods with USDA down give three `unavailable` lines and one search); WARNING for a failure, INFO otherwise (`code`, the tool's `status`), never the food's name. The ERROR record `turn_error` is the catch-all's (T1.8). T9.8 puts the same `turn_id` on the LangSmith trace.

**Tracing (T9.8, D19, Sprint 3 Hard 2).** `src/tracing.py` sends the run tree of every chat turn, conversation, coach's card answer, weekly review run and decision, evaluation turn, and a scored evaluation's judge calls to LangSmith (the EU region), with the data masked. It is off unless the app's flag `FITCOACH_TRACING` and the key `LANGSMITH_API_KEY` are both set (secrets.toml or the environment; the key read only by `config.get_langsmith_api_key()`). `configure_tracing()`, run by `configure_logging()`, sets LangSmith's global state on each run of the page or a script: off, it turns tracing off for every LangChain run, so LangSmith's own `LANGSMITH_TRACING` flag is ignored; on, it installs one `langsmith.Client` whose anonymizer is `tracing.mask()`, so every tracer LangChain makes sends through it and no code passes a tracer of its own (built once per key, reused on Streamlit's reruns). `mask()` runs on each run's inputs, outputs, metadata and error before it leaves the machine: it keeps the shape where something is kept (plain identifier keys, lists, dicts; a record or a list with nothing kept becomes one `[masked]`), token counts, the turn's counters, LangGraph's node fields, the model name, the app's tool names, statuses, turn kinds and codes, and `turn_id`; every other text and number becomes `[masked]`, a tool call's arguments are masked whole, an error keeps its class name. Each run carries the `turn_id` of its log lines as metadata (`graph.run_config(turn_id)`, `Conversation.config(turn_id)`, the review's run config; a review run or decision, and a coach's answer on the card, get an ID of their own; the judge of a scored evaluation, `eval_scoring.Judge.for_turn()`, calls under the `turn_id` of the answer it scores, code review round 8), so a log line and a trace can be matched. What is sent and the limits: `docs/SECURITY.md`, the LangSmith row.

## 14. Risks and early checks

- **Embeddings through OpenRouter with `OpenAIEmbeddings`:** by default it may send token arrays instead of text, which OpenRouter may not accept; set `check_embedding_ctx_length=False`. Set in T1.2 (`src/llm.py`, and a unit test checks the raw text goes out); confirmed by one live call run by the owner (O5, `scripts/live_check_llm.py`).
- **Source #1 download:** resolved in T2.1 (Europe PMC has it); see section 4.
- **gpt-5 models:** no `temperature`; reasoning tokens add cost, so `max_tokens` and the reasoning effort (`low`, T1.2) are set in config.
- **Long waits:** the OpenAI SDK honours a server's `Retry-After` up to 2 minutes per retry, so in the worst case one call waits about 7 minutes (3 timeouts of 60 s plus 2 waits of 120 s) before the error shows, and a turn makes several calls. The 60 s limit applies to each phase of a request (connect, each read), not the whole request: a server that keeps sending bytes (e.g. keep-alive whitespace) could keep one request open longer, so 7 minutes is not a hard limit. Not observed with OpenRouter so far. Abandoned requests after our timeout may still be billed by the provider. Accepted in T1.2; lower `LLM_MAX_RETRIES` or the timeout if it is a problem in practice.
- **Deadline (2026-11-02, 14 days):** if time runs short, cut in this order: `evaluate_meal_plan`, the PDF (or its styling), token cost, chart polish. The core requirements and the optional tasks for maximum points (Medium 3, 6; Hard 1) come first (`docs/IMPLEMENTATION_PLAN.md`).

## 17. The agents: how they work, function calling, design and kinds (T9.11)

The Sprint 3 brief asks how agents work, how they differ, and how function calling is implemented (`docs/BRIEF_SPRINT3.md`, "Evaluation"). This section answers for this app; sections 2 and 16 hold the details.

### 17.1 How the two AI parts work

The app has two AI parts. The **chat** is an agent: the model chooses its next step from what its tools return. The **weekly review** is a workflow: the code fixes the steps and the model writes one of them.

| | The chat (guests and coaches; D9-D12, T9.2-T9.7, T9.17, T9.20) | The weekly review (coaches; D17, T9.16) |
|---|---|---|
| Started by | A question typed in the chat | The coach pressing "Draft weekly review" under a finished week |
| Who decides the next step | The model, in a loop: search, call a tool, both, propose a preference (coach), read a client's week (coach), or answer | The code: authorise, compute, retrieve, draft, validate, then the coach's decision; the graph's edges are fixed |
| Model calls | One per round, at most `MAX_TOOL_ROUNDS` (4) rounds plus one final call with no tools; each search also makes one query translation call | One draft with structured output (`WeeklyReview`), and one more only when the checks fail |
| Tools | The four Sprint 2 tools and `search_knowledge_base`; for a coach also `remember_preference`, `list_my_clients` and `get_client_week` (section 16, the table of tools) | None: the evidence search runs in code, with fixed queries for the topics the week's figures raise |
| Memory | Short-term: the session's earlier questions and answers (`InMemorySaver`, trimmed to `HISTORY_MAX_TOKENS`); long-term for a coach: the approved preferences in `<memories>` | The run's thread in a `SqliteSaver` (metrics, not chat), so a review waiting for the coach survives a restart |
| Person in the loop | Only for a preference: `interrupt()` pauses before anything is written, and the coach saves, edits or discards it | Always: `interrupt()` after the draft; the coach approves, edits or rejects, and the gymer reads only an approved review |
| Stops when | The answer has a basis (a passage within the distance limit, or a tool result), the round's searches found none (`NO_SOURCES_MESSAGE`), or the round limit is reached | The draft passes the checks and the coach decides, or it fails twice, or access is refused at any step |
| Checked in code | The input guard before any call; every tool argument against its schema; the round and search limits; the profile read from the app, never from the model | Access (role, relationship, scopes), the figures, every citation against the run's chunks, the calorie floor, no diagnosis, no training program, the numbers against the metrics |

The two parts share the session's rate limit (a review start counts as a question; the review runs none of the guard's content checks, as no user text reaches its model), the knowledge base, the model clients (`src/llm.py`), the masked tracing and the logs; neither calls the other.

### 17.2 How function calling is implemented

Function calling is the OpenAI-compatible tool calling that OpenRouter passes on: the request lists the tools with a JSON schema each, and the model's reply may hold tool calls (a name and JSON arguments) instead of, or beside, text. In this app:

1. **Tools are declared with schemas.** Each tool is a LangChain `StructuredTool` with an explicit Pydantic `args_schema` that holds only what the model may send: `registry.build_tools()` (`src/tools/registry.py`) makes the four Sprint 2 tools (`FoodLookupArgs`, `MealPlanArgs`, `NoArgs` for the energy tools) and, for a coach, the client tools (a client reference); `search.search_tool_definition()` adds `search_knowledge_base` (`SearchArgs`) and `preferences.tool_definition()` adds `remember_preference` for a coach, both joined in `graph._tools()`. They are built for each turn and role, so a guest is never offered a coach tool (D11), and the energy tools are bound to the session's profile, which the model can neither read nor change.
2. **The model gets them with `bind_tools`.** The graph's `agent` node binds the turn's tools to the chat model on every call (with `tool_choice="none"` after the last round); only the tools are passed at call time, never the model, `max_tokens` or a base URL (`.claude/rules/security-privacy.md`), so the allowlist and the cap set when the client was built hold.
3. **The graph routes a reply with calls to the tools.** `after_agent()` (our own edge, not `tools_condition`, as a reply whose only calls are not JSON is a round too) sends it to LangGraph's `ToolNode`; any other reply is the answer, or "not covered" while the answer has no basis.
4. **Every call is checked before it runs.** The `ToolNode`'s `wrap_tool_call` is `run_checked_call()`: it applies the round's limits (`MAX_TOOL_CALLS_PER_ROUND`, `MAX_MEAL_PLAN_CALLS_PER_ROUND`), and runs the call with its arguments validated against its schema first: a tool through `registry.run_tool_call()` (LangChain skips that check for a schema without fields), the search through `search.run_search()` (its own `SearchArgs` check and limit, `MAX_SEARCHES_PER_TURN`), the preference proposal through `preferences.propose()` (its own check; it writes nothing). A refused call, an unknown tool or a failing tool gets a fixed message as its result, never the exception's text or the model's arguments (section 10).
5. **The result goes back as a tool message.** The tool's result is JSON, escaped like every block (`escape_prompt_data()`), in a `ToolMessage`; a search returns its chunks in a delimited `<sources>` block. `end_round` answers the calls whose arguments were not JSON and counts the round, and the model is called again with the results.
6. **The loop ends.** After `MAX_TOOL_ROUNDS` rounds one last call with `tool_choice="none"` must answer; tool calls in it end the turn with a fixed error. A turn makes at most five answer-model calls.

The weekly review uses no tool calling: its draft uses structured output (`with_structured_output(WeeklyReview)`), the same JSON-schema mechanism used to force one reply shape, and its checks run in code. Query translation inside each search uses structured output too (`QueryPlan`, section 2, step 3a).

### 17.3 Why this design over others

| Design | What it would give | Why we did not choose it |
|---|---|---|
| **A fixed chain** for the chat (Sprint 2's D1 and D2: guard, query translation, retrieval, then an answer step with tools) | One predictable path, easy to test | Every question paid for a search, and a food or calculator question still sent six unrelated passages to the model (the Sprint 2 review, point 3); the chain could not choose between searching and a tool. Replaced by the agentic search (D10, T9.3). We kept a fixed chain where the steps never change: the weekly review |
| **LangChain's `create_agent`** (the prebuilt ReAct loop, with middleware such as `HumanInTheLoopMiddleware`) | The same loop in fewer lines | The input guard must end a turn before any paid call, an approval must pause at a node we choose, and a reply whose only calls are not JSON must count as a round; we also test each node and edge with fake models (D9). We built the same ReAct loop by hand from the parts `create_agent` uses (`StateGraph`, `add_messages`, `bind_tools`, `ToolNode`), so every step is ours to check |
| **Several agents** (e.g. a supervisor with a nutrition agent, a training agent and a review agent) | Separate prompts per domain | One guard and one loop to test; nutrition and training share one search, one coverage gate and one citation check (D22); a tool set per role keeps the roles apart (D11); more agents would mean more model calls, cost and waiting, and harder traces |
| **A free agent for the weekly review** | It could choose its own steps | The figures must be computed, not guessed, the citations checked and a person must decide before the gymer reads anything (D17); a fixed workflow gives each step its own rule and test |

### 17.4 The kinds of agent, and which kind each part is

The course describes six kinds of agent, from the simplest to the most complex. In our own words:

1. **Simple reflex:** reacts to the current input only, with fixed "if this, then that" rules; it remembers nothing.
2. **Model-based reflex:** still follows rules, but keeps an internal state about what the current input does not show, built from earlier inputs, and its rules read that state.
3. **Goal-based:** chooses its actions by whether they bring it closer to a goal, can take several steps, and decides when the goal is reached.
4. **Learning:** changes its own behaviour over time from feedback on how well it did.
5. **Utility-based:** scores the possible outcomes with a utility measure and picks the best one, trading goals off against each other.
6. **Multi-agent:** several agents with their own roles that work together or hand work to each other.

| Part of the app | Kind | Why |
|---|---|---|
| The input guard's checks (length, cleaning, prompt injection, the domain guardrails, the pain and injury guard; `src/guard.py`, `src/guardrails.py`) | Simple reflex | Fixed rules on the current message only: the same text always gets the same verdict, and nothing earlier is read |
| The input guard with its rate limit (`RateLimiter` in the session) | Model-based reflex, a minimal one | The limiter keeps the times of the session's accepted questions and review starts (a rolling window and a session total), a state the current message does not show, and the rule "refuse when the window or the total is full" reads it. Its model of the world is only those counts, so the guard as a whole is a model-based reflex part, while its content checks alone are a simple reflex |
| The chat (T9.2-T9.4, T9.7, T9.17, T9.20) | Goal-based (a ReAct loop) | Its goal is an answer with a basis. The model picks the next action from what the tools return (search, which tool, both, a second search, or answer) and decides when to stop, within the round and search limits. The session's earlier turns are its model of the conversation (T9.4), and for a coach the approved preferences are standing facts about how the coach works (T9.7) |
| The weekly review (T9.16) | A workflow, not an agent in this sense | The path is fixed in code and the model never chooses a step: it writes one draft. The validate step tests a goal (a draft that passes every check) and allows one redraft, which is the only goal-based trait; the person, not the program, makes the decision. Of the six kinds it is closest to a model-based reflex with one goal check: its state is the week's figures and the evidence found for them |
| Query translation inside each search (T3.2) | Not an agent | One model call with a fixed output shape, run by the search tool; it chooses no action |

**The kinds the app does not use, and why:**

- **Learning:** no part changes its own behaviour from feedback. The coach's saved preferences (T9.7) are memory the coach approves, read as text in each later chat; the model is not trained or tuned on them, and there is no rating of answers (Sprint 3's Medium 5 and Hard 4 were not chosen).
- **Utility-based:** no candidate answers or actions are scored against each other. Retrieval ranks passages (RRF and the distance gate) and DeepEval scores answers offline (T9.10), but neither chooses what the agent does.
- **Multi-agent:** one graph builder with a tool set per role (D11). The chat and the weekly review are separate graphs that never call each other or hand off work, and query translation is a single call inside a tool, not an agent of its own.
