## 2026-11-18 · T10.6 Prompt caching: the cached share per turn in Details, and a system prompt that stays the same within a turn · NMH1988/fitcoach-ai-assistant#144 (closes NMH1988/fitcoach-ai-assistant#138)
- **Brief:** Sprint 3 (`docs/BRIEF_SPRINT3.md`): Sprint 3 review point 5 (the cost of the long system prompt); Medium 1 (token usage and cost); Sprint 2 (`docs/BRIEF.md`): Medium 5 (token usage and cost display).
- **What:** `tests/test_agent_graph.py` runs the longest turn (`MAX_TOOL_ROUNDS` + 1 answer calls), for a guest and for a coach with a history and `<memories>`, and checks that every call sends a byte-identical system message and tool list. `src/usage.py`: `CallUsage.cached_input` (capped at the input), `call_saving()` (cached input x (input price - cache price), 0 with no cached input or no cache price, never negative, None when the price is unknown), `TurnUsage.savings`, `input_tokens`, `cached_tokens` and `saved`, `answer_calls()`, `cached_percent()`, and `ANSWER_STEP` (moved from `views/tables.py`). `views/tables.cache_line()` and three texts in `src/i18n.py` (English and German): the cached share and the saving, the share with "not known" when a price is missing, or "none of this answer's input came from the provider's prompt cache"; `views/usage_view.section()` shows it right below the Details tab's table. `scripts/run_evaluation.py` prints, after the totals, the cached share of the answer calls over each question's first run, round 1 apart from the later rounds (`cache_lines()`). `docs/ARCHITECTURE.md` section 9 ("Prompt caching") and `docs/TESTING.md` ("Prompt caching (T10.6)").
- **Why:** the reviewer asked to show how much of the long system prompt the provider's cache serves, with the prompt kept byte-identical within a turn. The code already kept it so (`prepare()` builds the system message once; the tools are built once a turn and bound in the same order), so the tests pin it rather than change the graph. Round 1 gets its own evaluation line because only a turn's first answer call shares nothing but the static prompt and the tools with earlier turns; later rounds also repeat the turn's own messages, which would inflate the share. Only each question's first run counts (code review rounds 1 and 2): a repeat from `--repeat` and a question's "(no profile)" variant send its round 1 again word for word (the profile is never in the messages, T9.3), so the cache could serve the question too.
- **Decisions & gotchas:** the Details share is over all the turn's input tokens (the rewrite and the search embedding included), as the criterion words it; the evaluation's is over the answer calls only, as its criterion words it (Claude's defaults, approved by the owner with the plan, 2026-11-18). The evaluation's lines are printed and in the `.md` report only, not in the results `.json`, so the baselines and the results-file checks are unchanged. "At today's prices" means the prices read for the turn (kept for a day, `usage.PRICES`). The last answer call of a turn differs only in `tool_choice="none"`, which is not part of the request's start. No prompt or tool binding changed, so no `/security-review`; no personal data, source, dependency, service or medical text changed, so no compliance run (`.claude/rules/workflow.md`).
- **Measured (O13, criterion 3):** the owner's run of the same day (`python -m scripts.run_evaluation --repeat 3` from the worktree at b2823fc, 51 runs, $0.0948): answer calls round 1 85% cached, later rounds 86%, so the provider's cache absorbs the static prompt; the run is also above the baseline (found 0.7647, cited 0.7451).
