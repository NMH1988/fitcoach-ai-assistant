- **Why:** the table lacks common foods (oils, butter, tofu, whey); asking the API only when the table has no match keeps the table's tested matches and the evaluation baseline as they are, and spends the key's quota only where it helps. The standard library's `urllib` (as for the price lists) adds no dependency and writes no log lines; the key in a header keeps it out of every URL. The answer is ranked with the table's own match, so "a match" means the same thing for both sources.
- **Decisions & gotchas:**
  - The owner's choices in the Question phase (2026-11-06): rule 10 changed as proposed; Foundation, SR Legacy and Survey (FNDDS) only (Branded and Experimental excluded, as USDA's pages do not confirm CC0 for them, rule 2); the chat's food tool only (not the meal plan check, the diary or the Food lookup tab); the key (O12) comes later, as tests need none. Defaults stated then: only `not_found` asks the API, nothing is stored, the evaluation run passes no client.
  - USDA's OpenAPI description names the nutrient fields `number` and `amount`, and documents the key only as `api_key` in the query; answers are commonly seen with `nutrientId` and `value`, and api.data.gov documents the `X-Api-Key` header. The parser reads both forms; the live check (O13) confirms the shape and the header.
  - Running `python scripts/generate_attribution.py` from a worktree imports `src` from the main checkout (the editable install) and writes there: use `python -m scripts.generate_attribution` from the checkout you mean, as CLAUDE.md says for the evaluation.
  - Found in passing, not changed here (T1.12): `configure_logging()` keeps `openai`, `httpx` and `httpcore` at WARNING, but the OpenAI SDK 3.x sends through `httpx2` and `httpcore2`, whose loggers are not in that list.
