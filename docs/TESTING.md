# Testing

How the project is tested, and where evaluation results and live checks are recorded. The short rules for writing tests are in `.claude/rules/testing.md`.

## Test levels

| Level | What | How |
|---|---|---|
| Unit | Pure logic: TDEE and macro calculators, calorie floor, unit conversion, profile validation, input guard, JATS parsing and chunking, metadata filters, RRF, citation formatting, token cost, PDF content | pytest; known-answer tests (e.g. TDEE for a fixed profile), conversions tested both ways, RRF on a hand-computed example |
| Integration | The pipeline end to end without the network: ingest -> Chroma -> query translation -> hybrid retrieval -> answer step with tools | `DeterministicFakeEmbedding` (langchain-core); Chroma in-memory or in a temp dir; a scripted fake chat model that returns fixed rewrites, tool calls and answers |
| UI | Visible behaviour of `app.py`: chat, sources, tool results, progress, settings, profile form, PDF button, error messages | `streamlit.testing.v1.AppTest` with the pipeline faked. This is our end-to-end level |
| Live (manual) | Real models and the real index | Run by the owner; results recorded below, never in CI |

Browser end-to-end tests (e.g. Playwright) are not planned: AppTest covers the UI logic, and the deadline is short.

## Rules

- No real network in tests: OpenRouter, embeddings and USDA are always faked. The suite passes with no API key; test keys are obvious fakes like `sk-test-not-a-real-key`.
- Every ticket's acceptance criteria map to tests or to named manual checks listed in the PR.
- Guard tests use attack strings and benign strings, so both missed attacks and false positives are caught.
- Test fixtures use only approved sources or text we wrote ourselves.

## CI

`.github/workflows/ci.yml` (added in the setup ticket, as in Sprint 1) runs on every push to `main` and every PR: `ruff check .`, `ruff format --check .`, `pytest` with coverage, and `pip-audit`.

## Evaluation

- **System prompt and answers:** the owner drafts the evaluation questions; results go here.
- **Retrieval:** a small set of questions with the source each should find, comparing vector-only, keyword-only and hybrid retrieval. This checks the hybrid search (Hard 1); it is not the full RAG evaluation (Hard 7).

The evaluation run (T6.1) asks the owner's questions through the app's whole chat turn; its results, the known problems and the suggested improvements are under "Evaluation results (T6.1)" below. The retrieval comparison (T3.6) is under "Retrieval comparison results (T3.6)".

How to run the retrieval comparison (T3.6, O5; the script is from T3.3): the owner writes the evaluation questions (O2) into `data/eval_questions.json`, a JSON list of objects such as `{"id": "q1", "question": "...", "expected_sources": ["4"], "good_answer": "..."}` (`expected_sources` are source IDs from `data/sources.json`; an empty list marks a question the sources should not cover, shown but not scored; `good_answer` is for T6.1 and ignored here). Then, with the index built and the key set up, `python scripts/compare_retrieval.py` (or `.venv\Scripts\python.exe scripts/compare_retrieval.py`, optionally with another file's path). Each question goes through the guard and costs one embedding call; it is searched alone, with no rewrites and no filter, so only the method differs: vector search with the distance limit, BM25, and the app's hybrid search. The script prints, per question, the rank of the first expected source in each method's top 6 and the sources found, then each method's hit rate and how many hybrid chunks were found by keyword only (marked `*` in the hybrid row). It never prints the key. Record the hit rates and the run in the "Live checks" table below, with a T3.6 (O5) row.

The owner's questions are in `data/eval_questions.json` (16, from T3.6) and `data/eval_questions_de.json` (5 German ones for T7.2, same format). The German file is kept apart because the script searches each question as written, with no rewrite into English, so German questions would lower the T3.6 hit rates; run it with the script only to see what German questions find before T7.2. `tests/test_eval_questions.py` checks that both files load, have unique IDs, name only sources in `data/sources.json` and give every question a `good_answer`, and that q13's fixed `profile` (T6.1) gives the targets its good answer names.

How to run the evaluation (T6.1, O5): with the index built and the key set up, `python scripts/run_evaluation.py` (or `.venv\Scripts\python.exe scripts/run_evaluation.py`; optionally another questions file, and `--repeat N` to ask each question N times). Each question goes through `chat.run_turn()`, the function the app calls (guard and guardrails, query translation, hybrid search, the answer model with its tools), with the app's models. A question with a `profile` (q13: a made-up profile, not a user's) runs with it, then again with no profile; the others run with none, as a new visitor asks them. The script prints, per run: how the turn ended (answer, no_sources, guardrail, rejected, error, with the fixed message), the plan's `needs_tool` and `needs_profile`, the filters, whether the profile block was sent, the sources found in `[S#]` order (`*` = found by keyword only), the sources cited with their labels, whether the expected sources were found and cited (with none expected: whether the answer cites nothing), the tools called with their status, and the tokens and cost; then the totals. It writes the full report (each answer, its tool results and the whole text of every chunk found) to `data/eval_runs/run-<date>-<time>.md`, which is gitignored as it holds article text; the citations are judged from it against each `good_answer`. It never prints or writes the key and exits with 1 if any turn ended in an error. Then the owner asks q13 (with and without a profile) and q14 in the app itself, to see the "Add your details" button and the Tool results. Record the results below ("Evaluation results (T6.1)") and in the "Live checks" table, with a T6.1 (O5) row.

### Known problems and suggested improvements (T6.1)

From this run, the T3.6 comparison and the earlier live checks. Ordered by impact; each has a suggested fix, none built in T6.1.

1. **A filter the plan should not set can hide the main source (q9).** The query translation model (`gpt-5-nano`) set `evidence_tier` 2 for a question that asks for no kind of source, against its prompt (O7). Because the filtered chunks still passed `RETRIEVAL_MAX_DISTANCE`, the filter was kept (T3.2's rule), and the HMB position stand never reached the answer. Suggested fix: enforce the prompt's rule in code, keeping `evidence_tier` (and `min_year`) only when the question itself names a review, meta-analysis, position stand or year; or search with and without the filter and fuse the lists, so a filter can rank sources but not remove the best one. Re-run q9 with `--repeat 3` after the fix.
2. **Citations drift onto added advice (q7, q10, q11, q13).** Each answer's main claims match their chunks, but practical sentences the model adds (see a professional, replace fluids after every session, a range from another chunk) carry an `[S#]` whose passage does not say it. It goes against rule 7 of the copyright policy (never attribute a claim the source does not make). Suggested fix (the owner's prompt, O1): cite a sentence only when the passage states it, and leave general advice uncited and marked as general. A later, automatic check (claim against chunk) would be the RAG evaluation of Hard 7, which the brief lists as optional.
3. **Near-domain questions pass the distance limit (q11, and q12 from T3.6).** "How much water…" found six chunks at 0.43-0.49, well inside 0.62, so the answer model got protein and nutrient-timing passages and used two of them for hydration advice. The answer still said the sources give no daily amount. Suggested fix: keep the limit (the nearest chunk of each covered question was at 0.22-0.31 here, and T3.1's calibration found long covered questions up to 0.54, so a lower limit would cut real questions) and tighten the prompt as in item 2; re-measure the limit on these 16 questions with `scripts/live_check_retrieval.py` before changing it.
4. **One source can fill all six places (q2, q3, q10: five or six chunks from one article).** Other expected sources (#15 for q1, #12 for q5, #8 for q10) did not reach the top 6. Suggested fix: cap chunks per source (e.g. 3 of 6) or use MMR when building the fused list, so a second article gets in; check with `scripts/compare_retrieval.py` that hit rates do not drop.
5. **Tool questions still send six research passages (q14).** A food lookup got six unrelated chunks (four within the limit at 0.54-0.58, two keyword only), which cost input tokens and invite a stray citation (none this time). Suggested fix: when the plan says `needs_tool` and the nearest chunk is far (e.g. above 0.5), send no passages; measure on q13 and q14 first.
6. **A general question can trigger the targets tool (q1).** The plan marked "how much protein should I eat each day" as needing the tool and the profile, so with no profile the answer opened with "add your details" before the research answer, at about 6,000 more tokens. This follows the owner's rule for personal advice (O1, O7); the owner may prefer the research answer first and the pointer at the end.
7. **Small wording issues against the good answers:** q2 calls 0.55 g/kg a per-meal "ceiling"; q13 does not point to Tool results (in the script's run and in the app) and, in the app check only, does not call its values estimates. Suggested fix: the owner's prompt (O1) could say that per-meal amounts are targets, not limits of what the body uses, and repeat "say the values are estimates and point to Tool results".
8. **One run per question.** T3.6 finding 6 showed the chunk lists move between runs, so a single run can miss or show a problem by chance (q9's filter may not be set every time). Suggested: run the set with `--repeat 3` after any retrieval or prompt change and compare by cited sources, not exact chunk lists.

Known problems found before T6.1, still open (details in the "Live checks" rows and in `docs/SECURITY.md`):

9. **Short rewrites can bring an off-topic question to the answer call** (T3.5, T3.7): one rewrite with a short acronym ("VAR and offside rule in football") passed the distance limit, so the offside question was answered by the model (declined in its own words) instead of the fixed "not covered" message. Suggested: apply the distance limit to the question as well as the rewrites, or require two queries to pass it.
10. **Food matching is weak for bare or missing names** (T4.3): "egg" gives a raw yolk, "chicken" a wing, "rice" black rice; oils, butter, whey, tofu and pizza are not in the Foundation Foods table. The answer shows the matched name and alternatives, so the user can see it. Suggested: a small table of common default matches, or another USDA table for missing foods (licence to check first).
11. **Hybrid search is not shown better than vector search on real questions** (T3.6): both found every expected source; its value is shown only by the "HMB" fixture test. Suggested: a harder question set (abbreviations, product names, typos).
12. **German answers are not measured yet** (T7.2): the German questions were only searched as written (T3.6).
13. **The distance limit (0.62) rests on about 40 questions** (T3.1's 28 and these 16); here the nearest chunk of each covered question was at 0.22-0.31, of q12 at 0.37 and of q11 at 0.43.
14. **Known limits accepted earlier:** the input guard and guardrails are patterns, so reworded attacks or concerns can pass and are left to the prompt's rules (`docs/SECURITY.md`); the dark-mode Save button text is 3.4:1 (T7.3).

What the run shows, and follow-ups for T6.1's reflection:

1. **Hybrid matched the best method but did not beat vector search on this set.** Both found every expected source; keyword search missed q1 ("protein each day": its top 6 came from #14, #13, #9, #12 and #10, none from #7, #11 or #15) and ranked low on q4 (5) and q7 (4), where common words outweigh the topic word. Hybrid never lost a hit that vector search had, and it fixed keyword search's misses. The questions are phrased close to the sources, so vector search is at its ceiling here; the case where keyword search adds a hit (an exact term the embedding misses) is shown by the fixture test of AC-4 (the "HMB" test in `tests/test_chat.py`), not by this set. Follow-up: a harder set (abbreviations, product names, typos) would show whether hybrid adds hits on real questions.
2. **Hybrid moved q1's first expected source from rank 1 to 2.** A per-meal chunk (#13) ranked second in both lists and won the fusion. Harmless here, as the answer step gets all 6 chunks.
3. **q8 (caffeine): #12 ranked first in every method in both runs.** The contest-preparation review also discusses caffeine, so it is a relevant source, not noise; after the first run (where #6 was the only expected source and every method found it at rank 2) the owner added `"12"`, so q8 now scores rank 1 in every method. The hit rates did not change.
4. **Keyword-only chunks fill a large share of the hybrid list:** 32 of 84 chunks (38%; 31 in the first run) in English, 12 of 30 in German. For the near-domain questions q11 (water) and q12 (vitamin D) some vector hits passed `RETRIEVAL_MAX_DISTANCE`, so retrieval treats them as covered and keyword-only chunks (e.g. #20 for water, #10 for vitamin D) join the list; only the answer step can say the sources do not cover them. No article gives a daily water target. For vitamin D the articles give no recommended dose, but #4 notes, citing other work, that vitamin D matters for muscle development and strength, particularly in people with low levels, reports that HMB's strength benefit in a 12-month study of older adults depended on vitamin D status, and lists studies that paired HMB with vitamin D3, and #3, #11 and #12 mention vitamin D too, so a grounded answer to q12 may cite #4 on vitamin D status as long as it gives no dose as advice. Follow-up for T6.1: check that the answer to q11 says the sources do not cover it and cites nothing, and that the answer to q12 gives no recommended dose and cites only what the sources say; if either cites a keyword-only chunk that does not support its claim, consider a limit (a minimum BM25 score, or at most 2 keyword-only chunks in the top 6).
5. **German questions searched as written:** keyword search found nothing for de2 and little that matched elsewhere, as the index is English; vector search (a multilingual embedding model) still found every expected source. In the app the query translation step (T3.2) rewrites every question into English first, so these numbers are not the app's German retrieval; T7.2 measures that. de4 (oats) shows the keyword-only effect most: one vector hit passed the limit and five keyword-only chunks filled the list.
6. **The lists move a little between runs.** In the second run, questions that did not change came back with a slightly different order or set of chunks (the vector lists of q11, q12 and q13; the last hybrid chunk of q7), while the rank of every expected source stayed the same. The index and the code were the same, so the likeliest cause is that the embedding API returns slightly different vectors for the same text on different calls, which moves chunks near the distance limit or at the bottom of the top 6. For T6.1: compare answers by whether they cite the right sources, not by the exact chunk list, and do not read a one-run difference of one chunk as a regression.

## Live checks

Record only what was actually run and observed: date, model, what was checked, result.

How to run the T1.2 check (O5): from the repo root, with the key set up as in the README, `python scripts/live_check_llm.py` (on Windows without an activated venv: `.venv\Scripts\python.exe scripts/live_check_llm.py`). It prints the model, reply length, token use and embedding size (never the key), or the mapped error.

How to run the T5.1 cost check (O5): the same command as the T1.2 check. Since T5.1 it makes two chat calls and prints cost lines for each: a plain call ("cost (app)", "cost (OpenRouter)"), and a call streamed through `chat.stream_reply()` with a usage recorder, as the app's answer rounds are ("chat (streamed, as the app's answer rounds)" with the tokens the app records, then "cost (app, streamed)", "cost (OpenRouter, streamed)"). "cost (app)" is what the app computes from OpenRouter's prices and the reported tokens (input and output tokens; the reasoning count is shown, not priced); "cost (OpenRouter)" is the cost and the native prompt, completion and reasoning tokens OpenRouter recorded for that call (`GET /api/v1/generation`, asked with the key, up to 5 times 2 s apart while it is not recorded yet; the streamed call's ID is read from the stream, which langchain drops). Check three things: the streamed call's recorded tokens match OpenRouter's native tokens (not doubled, not missing: "the stream reported no token use" means the app would count no answer round); each pair of costs matches to rounding; if OpenRouter's is higher by about the reasoning tokens times the completion price, reasoning is billed on top of the output tokens and `usage.call_cost()` must add it. Run it without a proxy: the streamed call's own transport ignores `HTTPS_PROXY`. Record all the lines.

How to run the T2.3 check (O5): after `python scripts/download_sources.py`, from the repo root with the key set up, `python scripts/build_index.py` (or `.venv\Scripts\python.exe scripts/build_index.py`). It prints its progress per batch and then the chunk, source and character counts (never the key). Stop the app first if it is running (it keeps the old collection open) and restart it afterwards.
