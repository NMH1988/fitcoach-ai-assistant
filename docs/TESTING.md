# Testing

How the project is tested, and where evaluation results and live checks are recorded. The short rules for writing tests are in `.claude/rules/testing.md`.

## Test levels

| Level | What | How |
|---|---|---|
| Unit | Pure logic: TDEE and macro calculators, calorie floor, unit conversion, profile validation, input guard, JATS parsing and chunking, metadata filters, RRF, citation formatting, token cost, PDF content | pytest; known-answer tests (e.g. TDEE for a fixed profile), conversions tested both ways, RRF on a hand-computed example |
| Integration | The pipeline end to end without the network: ingest -> Chroma -> query translation -> hybrid retrieval -> answer step with tools | `DeterministicFakeEmbedding` (langchain-core); Chroma in-memory or in a temp dir; a scripted fake chat model that returns fixed rewrites, tool calls and answers |
| UI | Visible behaviour of `app.py` and `views/`: chat, sources, tool results, progress, settings, profile form, PDF button, error messages | `streamlit.testing.v1.AppTest` with the pipeline faked. This is our end-to-end level |
| Live (manual) | Real models and the real index | Run by the owner; results recorded below, never in CI |

Browser end-to-end tests (e.g. Playwright) are not planned: AppTest covers the UI logic, and the deadline is short.

## Rules

- No real network in tests: OpenRouter, embeddings and USDA are always faked. The suite passes with no API key; test keys are obvious fakes like `sk-test-not-a-real-key`.
- Every ticket's acceptance criteria map to tests or to named manual checks listed in the PR.
- Guard tests use attack strings and benign strings, so both missed attacks and false positives are caught.
- Test fixtures use only approved sources or text we wrote ourselves.

## CI

`.github/workflows/ci.yml` (added in the setup ticket, as in Sprint 1) runs on every push to `main` and every PR: `ruff check .`, `ruff format --check .`, `pytest` with coverage, and `pip-audit`.

## Evaluation

- **System prompt and answers:** the owner drafts the evaluation questions; results go here.
- **Retrieval:** a small set of questions with the source each should find, comparing vector-only, keyword-only and hybrid retrieval. This checks the hybrid search (Hard 1); it is not the full RAG evaluation (Hard 7).

The evaluation run (T6.1) asks the owner's questions through the app's whole chat turn; its results, the known problems and the suggested improvements are under "Evaluation results (T6.1)" below. The retrieval comparison (T3.6) is under "Retrieval comparison results (T3.6)".

How to run the retrieval comparison (T3.6, O5; the script is from T3.3): the owner writes the evaluation questions (O2) into `data/eval_questions.json`, a JSON list of objects such as `{"id": "q1", "question": "...", "expected_sources": ["4"], "good_answer": "..."}` (`expected_sources` are source IDs from `data/sources.json`; an empty list marks a question the sources should not cover, shown but not scored; `good_answer` is for T6.1 and ignored here). Then, with the index built and the key set up, `python scripts/compare_retrieval.py` (or `.venv\Scripts\python.exe scripts/compare_retrieval.py`, optionally with another file's path). Each question goes through the guard and costs one embedding call; it is searched alone, with no rewrites and no filter, so only the method differs: vector search with the distance limit, BM25, and the app's hybrid search. The script prints, per question, the rank of the first expected source in each method's top 6 and the sources found, then each method's hit rate and how many hybrid chunks were found by keyword only (marked `*` in the hybrid row). It never prints the key. Record the hit rates and the run in the "Live checks" table below, with a T3.6 (O5) row.

The owner's questions are in `data/eval_questions.json` (16, from T3.6) and `data/eval_questions_de.json` (5 German ones for T7.2, same format). The German file is kept apart because the script searches each question as written, with no rewrite into English, so German questions would lower the T3.6 hit rates; run it with the script only to see what German questions find before T7.2. `tests/test_eval_questions.py` checks that both files load, have unique IDs, name only sources in `data/sources.json` and give every question a `good_answer`, and that q13's fixed `profile` (T6.1) gives the targets its good answer names.

How to run the evaluation (T6.1, O5): with the index built and the key set up, `python scripts/run_evaluation.py` (or `.venv\Scripts\python.exe scripts/run_evaluation.py`; optionally another questions file, and `--repeat N` to ask each question N times). Each question goes through `chat.run_turn()`, the function the app calls (guard and guardrails, query translation, hybrid search, the answer model with its tools), with the app's models. A question with a `profile` (q13: a made-up profile, not a user's) runs with it, then again with no profile; the others run with none, as a new visitor asks them. The script prints, per run: how the turn ended (answer, no_sources, guardrail, rejected, error, with the fixed message), the plan's `needs_tool` and `needs_profile`, the filters, whether the profile block was sent, the sources found in `[S#]` order (`*` = found by keyword only), the sources cited with their labels, whether the expected sources were found and cited (with none expected: whether the answer cites nothing), the tools called with their status, and the tokens and cost; then the totals. It writes the full report (each answer, its tool results and the whole text of every chunk found) to `data/eval_runs/run-<date>-<time>.md`, which is gitignored as it holds article text; the citations are judged from it against each `good_answer`. It never prints or writes the key and exits with 1 if any turn ended in an error. Then the owner asks q13 (with and without a profile) and q14 in the app itself, to see the "Add your details" button and the Tool results. Record the results below ("Evaluation results (T6.1)") and in the "Live checks" table, with a T6.1 (O5) row.

### Known problems and suggested improvements (T6.1)

From the two runs, the T3.6 comparison and the earlier live checks. Ordered by impact; each has a suggested fix, none built in T6.1.

1. **A filter the plan should not set can hide the main source (q9, 2 of 2 runs).** The query translation model (`gpt-5-nano`) set `evidence_tier` 2 in both runs for a question that asks for no kind of source, against its prompt (O7). Because the filtered chunks still passed `RETRIEVAL_MAX_DISTANCE`, the filter was kept (T3.2's rule), and the HMB position stand never reached the answer. Suggested fix: enforce the prompt's rule in code, keeping `evidence_tier` (and `min_year`) only when the question itself names a review, meta-analysis, position stand or year; or search with and without the filter and fuse the lists, so a filter can rank sources but not remove the best one. Re-run q9 with `--repeat 3` after the fix.
2. **Citations drift onto added advice.** Each answer's main claims match their chunks, but sentences the model adds (see a professional, replace fluids after every session, a vitamin D test, a range from another chunk) sometimes carry an `[S#]` whose passage does not say it: q7, q10, q11, q12 and q13 in the first run; q8, q12 and q13 in the second. The same question drifts in one run and not in the next. It goes against rule 7 of the copyright policy (never attribute a claim the source does not make). Suggested fix (the owner's prompt, O1): cite a sentence only when the passage states it, and leave general advice uncited and marked as general. A later, automatic check (claim against chunk) would be the RAG evaluation of Hard 7, which the brief lists as optional.
3. **Near-domain questions pass the distance limit (q11, and q12 from T3.6).** "How much water…" found six chunks at 0.43-0.49 in the first run (the smallest distance over the question and its rewrites; five vector hits at 0.43-0.47 and one keyword-only chunk in the second), well inside 0.62, and T3.8's gate did not stop it, so the question's own wording has a chunk within the limit too. In the first run the model used two of them for hydration advice; in the second it cited nothing. Both answers said the sources give no daily amount. Suggested fix: keep the limit (the nearest chunk of each covered question, over the question and its rewrites, was at 0.22-0.31, and T3.1's calibration, measured on questions as asked, found long covered questions up to 0.54, so a lower limit would cut real questions) and tighten the prompt as in item 2; re-measure the limit on these 16 questions with `scripts/live_check_retrieval.py` before changing it.
4. **One source can fill all six places (q2, q3, q10: five or six chunks from one article).** Other expected sources (#12 for q5, #8 for q10; #15 for q1 in the first run) did not reach the top 6. Suggested fix: cap chunks per source (e.g. 3 of 6) or use MMR when building the fused list, so a second article gets in; check with `scripts/compare_retrieval.py` that hit rates do not drop.
5. **Tool questions still send six research passages (q14).** A food lookup got six unrelated chunks in both runs (0.53-0.58 over the question and its rewrites), which cost input tokens and invite a stray citation (none so far). T3.8's gate does not stop it: the turn returned chunks on T3.8's code, so the question's own wording has a chunk within the limit. Suggested fix: when the plan says `needs_tool` and the nearest chunk is far (e.g. above 0.5), send no passages; measure on q13 and q14 first.
6. **A general question can trigger the targets tool (q1).** In the first run the plan and the model called the targets tool for "how much protein should I eat each day", so with no profile the answer opened with "add your details", at about 6,000 more tokens; in the second the model called no tool and still pointed to "Add your details". This follows the owner's rule for personal advice (O1, O7); the owner may prefer the research answer first and the pointer at the end.
7. **Small wording issues against the good answers:** q13 does not point to Tool results and does not name daily needs (2,759 kcal) in either run, and did not call its values estimates in the app check (it did in both script runs); q2 called 0.55 g/kg a per-meal "ceiling" in the first run (not in the second). Suggested fix: the owner's prompt (O1) could say that per-meal amounts are targets, not limits of what the body uses, and repeat "say the values are estimates and point to Tool results".
8. **The model can offer a calculation the app cannot do (q11, second run).** It offered to calculate fluid needs from "your stored profile" with the app's tools; no tool does that, and that run had no profile set (no profile block was sent). Suggested fix (O1): name what the tools can calculate and say not to offer other calculations.
9. **Answers vary between runs.** The second run differed from the first in citations (q7's misattributed advice gone, q11 cited nothing), tool calls (q1) and wording (q2), with the same code apart from T3.8 and T7.1, which do not touch these questions' retrieval. T3.6 finding 6 showed the chunk lists move too. Suggested: run the set with `--repeat 3` after any retrieval or prompt change and compare by cited sources and the share of runs with a problem, not by one run.

Known problems found before T6.1, still open (details in the "Live checks" rows and in `docs/SECURITY.md`):

10. **Short rewrites could bring an off-topic question to the answer call** (T3.5, T3.7): one rewrite with a short acronym ("VAR and offside rule in football") passed the distance limit, so the offside question was answered by the model. **Fixed by T3.8 (#72), merged after the first run:** only the question's own wording now decides coverage (the owner's check: 3 of 3 offside questions stopped). Still open from T3.8: a single letter or very short question can sit within the limit on its own, and vague or German questions whose own wording is far from the sources now get the "not covered" message.
